## 第1章 项目概述

### 1.1 项目名称
**智慧校园多智能体服务平台（Smart Campus Multi-Agent Service Platform）**

### 1.2 项目定位
一个面向高校选课场景的、基于多智能体协作架构的智能服务平台，底层由分布式缓存一致性治理平台（Hercules）提供高并发数据服务支撑，上层由多智能体系统提供智能决策能力，全链路具备零侵扰可观测性。

### 1.3 核心业务目标
| 序号 | 目标 | 量化指标 |
| :--- | :--- | :--- |
| 1 | 支持学生通过自然语言完成课程检索、推荐与预选 | 意图识别准确率 ≥ 90% |
| 2 | 保障高并发选课场景下的数据最终一致性 | 不一致窗口 < 2秒 |
| 3 | 缓存命中率 ≥ 95% | 读请求优先走缓存 |
| 4 | 全链路可观测，核心操作可追踪 | 覆盖100%关键Span |
| 5 | 支持500并发用户稳定运行 | JMeter压测通过 |

### 1.4 创新点摘要
1. **多智能体协作架构**：采用Spring AI Alibaba框架构建路由、推荐、排课、执行四类专业智能体，通过协作完成复杂选课任务。
2. **向量时钟并发冲突消解**：在分布式缓存更新中引入向量时钟机制，解决并发写覆盖导致的数据腐化问题。
3. **eBPF零侵扰可观测性**：利用eBPF技术实现无代码修改的全链路监控，覆盖从网关到数据库的完整请求路径。

## 第3章 系统架构设计

### 3.1 总体逻辑架构

系统采用**四层分离架构**，自下而上分别为：

| 层级 | 名称 | 职责 | 核心组件 |
| :--- | :--- | :--- | :--- |
| **L1** | 数据存储层 | 持久化存储与索引 | MySQL、Redis、Milvus、Neo4j |
| **L2** | 一致性治理层（Hercules） | 保障缓存与DB的一致性 | Canal、RocketMQ、向量时钟引擎、巡检引擎 |
| **L3** | 多智能体决策层 | 任务理解、分解与执行 | 路由智能体、课程推荐智能体、排课冲突智能体、执行智能体 |
| **L4** | 用户接入层 | 交互界面与API暴露 | Vue3前端、Spring Cloud Gateway |

**横切关注点**：可观测性（eBPF + OpenTelemetry + Grafana）贯穿L2-L4，提供全链路监控能力。

### 3.2 模块划分（Maven多模块结构）

```
hercules-platform/
├── hercules-common/               # 公共模块：工具类、常量、异常定义、向量时钟算法
├── hercules-cache/               # 缓存治理模块：多级缓存封装、Redis/Caffeine操作
├── hercules-sync/                # 数据同步模块：Canal监听器、RocketMQ生产/消费
├── hercules-inspector/           # 巡检引擎模块：定时巡检、一致性比对、补偿SQL生成
├── hercules-agent/               # 多智能体模块：Spring AI Alibaba智能体定义与编排
├── hercules-rag/                 # RAG检索模块：向量化、Milvus操作、Graph RAG

```

### 3.3 核心数据流设计

#### 3.3.1 智能选课流程（正向）
```
用户提问 → API网关 → 路由智能体（意图识别）
    ├─→ [查询类] → 课程推荐智能体 → 向量检索(Milvus) / 图查询(Neo4j) → 生成回复
    └─→ [操作类] → 排课冲突智能体 → 约束校验 → 执行智能体 → 写MySQL → 返回结果
```
所有读操作贯穿**L2缓存层**，所有写操作触发**L2一致性同步链路**。

#### 3.3.2 缓存一致性同步流程（异步）
```
业务写MySQL → Canal监听Binlog → 发送RocketMQ(顺序队列) → 向量时钟消费者
    ├─→ 版本比较（新/旧/并发）
    │   ├─→ 新：直接更新Redis + 失效Caffeine
    │   ├─→ 旧：丢弃（幂等）
    │   └─→ 并发冲突：执行合并策略 → 更新Redis → 记录冲突日志 → ES
    └─→ 更新t_cache_version表（记录向量时钟）
```

#### 3.3.3 巡检与自愈流程（兜底）
```
定时触发（每日凌晨） → 巡检引擎从MySQL从库分批读取数据
    → 多线程并发查询Redis对应Key
    → 比对update_time vs 缓存时间戳
    → [一致] 跳过
    → [不一致] 生成补偿SQL → 推送至RocketMQ修复队列
        → 修复Worker执行 → 更新Redis → 记录t_repair_log
```
