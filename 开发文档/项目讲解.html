Hercules 项目讲解

智慧校园多智能体服务平台 —— 缓存一致性治理与高并发选课

文档基线：2026-09-07（代码仓库 hercules-platform，commit aaea17e）· 本文整理自项目开发文档，出现的全部数字均标注出处章节。

1项目概述

Hercules 是一个面向高校选课场景的毕业设计项目。选课场景的典型压力是：开放选课的短时间内，大量学生同时查询课程、同时提交选课请求。

这个场景带来两个需要解决的技术问题：

  1. 读取次数远多于写入次数。课程信息被反复查询，如果每次都读数据库，数据库会成为瓶颈。解决办法是把读出来的数据放在缓存里重复使用，减少对数据库的访问。
  2. 数据修改后，缓存里留有旧数据。课程人数变了、课程信息改了，各处缓存必须更新，否则学生看到的是过期数据。解决办法是一条"修改数据库之后自动刷新缓存"的同步链路，并且能处理多个应用实例同时修改同一数据产生的冲突。
缓存：把从数据库读出的数据临时存放在更快的存储（内存或 Redis）里，之后的相同读取直接取用，不必再查数据库。 一致性：缓存里的数据与数据库里的数据保持相同。最终一致性：允许数据在极短时间内不一致（例如 10 秒），但保证此后恢复一致。

项目按"四层分离"的结构组织（见第 2 章），目前已完成的部分是：缓存一致性治理核心（多级缓存 + 向量时钟同步链）、登录认证、高可用防护、独立网关、日志体系、500 并发压测验证、真实 Binlog 同步链（Canal + RocketMQ），以及多智能体对话入口（自然语言推荐 / 冲突校验 / 确认制选课）。计划中的部分是：RAG 检索、巡检自愈、可观测性完善、Vue3 前端。

2总体架构

系统分为四层，上层调用下层，下层不感知上层：

L4 用户接入层
所有外部请求的统一入口。网关负责验证令牌签名、剥离伪造的内部请求头、生成追踪标识，然后转发给应用。前端提供学生操作界面与运维监控界面。
网关已实现 Vue3 前端规划中
L3 多智能体决策层
学生用自然语言提问，由四类智能体分工完成：路由（判断意图）、推荐（挑选课程）、排课冲突（检查时间与先修课约束）、执行（调用选课接口）。
对话入口已实现（阶段 D）
L2 一致性治理层（本项目的核心）
多级缓存（Caffeine + Redis）承担读压力；向量时钟同步链在数据修改后刷新缓存并消解并发冲突；定时巡检比对数据库与缓存、自动修复差异。
缓存与同步链已实现 巡检规划中（阶段 C）
L1 数据存储层
MySQL 8 保存业务数据，是唯一的数据事实来源；Redis 7 保存分布式缓存。后续接入 Milvus（向量检索）与 Neo4j（图查询）。
MySQL / Redis 已实现 Milvus / Neo4j 规划中
网关：一个独立运行的入口服务，外部请求先经过它再到达应用。统一做鉴权和记录追踪标识，业务应用本身不做这些重复工作。

第 4 到第 9 章说明的都是 L2 已实现部分的工作方式；L3 目前只有空模块占位，尚未编写代码。

3模块结构

Maven 多模块：把一个工程按职责拆成多个目录（模块），统一构建、统一管理版本。每个模块只暴露必要的接口给其他模块，改一处不会牵连全部代码。

hercules-gateway 是独立进程，不参与上述依赖链；它与 hercules-application 共享同一个令牌签名密钥，各自独立验签。

4机制一：多级缓存读路径

课程查询使用两级缓存加数据库的三层结构，按顺序查找：

命中 / 未命中：请求的数据在某一层存在称为命中，不存在称为未命中。cache-aside（旁路缓存）：读请求先查缓存，缓存没有再查数据库，查到后写回缓存。回填：把数据库查到的结果写回缓存，供后续请求直接命中。

4.1 读请求的处理顺序

1请求查询课程，先查 L1（Caffeine，本进程内存）
↓ 命中：直接返回（微秒级，最快）
2L1 未命中，查 L2（Redis，独立的缓存服务）
↓ 命中：写回 L1，返回
3L2 也未命中，查 MySQL
↓ 查到：写回 L2 和 L1，返回
4以上每一步都记录计数（L1 命中、L2 命中、数据库回源），供命中率统计与监控使用
TTL（Time To Live）：缓存条目的存活时间，到期后视为失效，下次请求重新加载数据。设置 TTL 的目的是限制"读到旧数据"的最长时间。

4.2 TTL 设计

缓存键类型L1（Caffeine）L2（Redis）设计意图
课程列表键 course:list:* 10 秒10 秒 列表数据随选课人数频繁变化。10 秒的 TTL 构成"最终一致窗口"：最坏情况下，用户看到的是 10 秒前的列表。
课程详情键 course:detail:{id} 60 秒300 秒 单条课程读多改少，允许更长的缓存时间；详情键纳入同步链，数据变更时会主动刷新，不依赖 TTL 到期。

L1 使用 Caffeine 的自定义 Expiry（过期策略）按键设置各自的 TTL，而不是全局统一时间；缓存总量有上限，超限时由 Caffeine 内置的 W-TinyLFU 策略淘汰访问频率最低的条目。

4.3 缓存键全景

键存储TTL语义
course:{id}L1 + L2L1 60s / L2 300s课程详情，纳入向量时钟版本链：写路径 / Canal 链路均经消费者应用（写 L2 + 失效 L1 + 更新 t_cache_version）

4.4 命中率统计

CacheStatsCollector 用原子计数器记录 L1/L2 命中、未命中、数据库回源次数，并计算总体命中率（L1 命中 + L2 命中，除以总读请求）。数据有两个出口：

  • GET /api/v1/cache/stats：人工查询接口（管理员权限）；
  • Micrometer 指标族 hercules_cache_*，经 /actuator/prometheus 暴露给 Prometheus 持续采集。
Micrometer：Java 的指标采集库，把程序内部的计数、状态转成标准的监控数值。Prometheus：按时序存放这些数值、提供查询的服务，配合 Grafana 画图展示。

5机制二：向量时钟同步链

这是本项目的核心机制，要解决的问题有两个：

  1. 数据在数据库里修改之后，各级缓存如何自动更新；
  2. 多个应用实例同时修改同一条数据、各自发出缓存刷新消息时，如何判断哪条消息代表更新的数据，以及两条消息互相覆盖不到对方时怎么办。
向量时钟：一种给数据变更打版本标记的方法。每个应用实例（节点）维护一张计数表，例如 {"node-1": 3, "node-sim": 1}。每次本地变更，把自己的计数加一。比较两组计数就能判断：A 的每一项都不小于 B 且至少一项更大 → A 发生在 B 之后；反之亦然；两边互有大小 → 两个修改互不覆盖（并发），谁也没有包含谁的信息。

5.1 写路径的完整流程

1业务事务在 MySQL 中执行并提交（例如选课扣减人数）
↓ 提交成功后
2Spring 的事务提交事件（AFTER_COMMIT）触发，生成一条版本变更消息：缓存键、新值 JSON、节点名、时间戳、向量时钟（在存量时钟基础上，本节点计数加一）
↓ 消息进入消费端
3消费端从 t_cache_version 表读取该键的存量时钟，与新消息的时钟比较，按第 5.2 节的规则处理
↓ 处理完成后
4更新 t_cache_version 中的时钟记录，供下一次比较使用
AFTER_COMMIT：Spring 提供的事务钩子——只有在数据库事务真正提交成功之后才执行的动作。它保证了"先提交、后同步"的顺序：缓存刷新失败不会影响已经落库的数据。

5.2 消费端判定规则

比较结果含义动作
AFTER（新消息更新） 新消息发生在存量数据之后，是确定的新版本 写入 Redis（L2）→ 删除 Caffeine 对应键（L1，迫使下次读取重新加载）→ 更新版本记录；"应用"计数加一
EQUAL / BEFORE（相同或更旧） 消息是重复投递，或者由更旧的状态产生 直接丢弃，不做任何修改，保证重复消息无害
CONCURRENT（并发冲突） 两个修改互不覆盖，例如两个节点同时改了同一条课程的不同字段 对新旧两个 JSON 值逐字段做 LWW 合并：每个字段取时间戳较新一方的值；合并后向量时钟取两边计数的较大值（并集）；"冲突"计数加一
幂等：同一条消息处理一次和处理多次，结果相同。网络重试、消息重复投递时系统不受影响。LWW（Last-Write-Wins，最后写入获胜）：同一个字段出现两个值时，保留修改时间较晚的那个。

5.3 版本记录的持久化

每个缓存键的向量时钟持久保存在 t_cache_version 表（一行一个键）。应用重启后判定依据不丢失；冲突发生的次数也作为指标 hercules_sync_* 暴露，便于监控。

5.4 当前形态与已知边界

  • 当前传输方式：两种可切换——`in-process`（默认）：消息在本进程内传递（Spring 事件总线），单节点下顺序有保证；`canal-mq`（阶段 B 已接入）：MySQL Binlog → Canal Server（MQ 模式投递）→ RocketMQ 顺序队列 → 应用消费者，业务事务只落库，缓存刷新完全异步。两种模式下消费端判定逻辑完全复用。
  • 已知限制（记录于《工作日志》已知事项 #9）：冲突合并时旧值取自 L2；如果该键恰好已从 L2 逐出，合并退化为整体采用新值，仅存在于旧值中的字段会丢失。此限制已知、已记录，待后续版本处理。
Binlog：MySQL 记录每一行数据变更的日志文件。Canal：伪装成 MySQL 从库、持续读取 Binlog 的组件，把"哪张表的哪行数据变了"转成消息。RocketMQ：消息队列服务，把消息先存下来再交给消费者处理，使数据库变更通知与缓存刷新解耦、可异步进行。

6机制三：防超选选课

要解决的问题：剩余名额 1 个，两个选课请求同时到达。如果"先查询剩余人数、再写入 +1"分两步执行，两个请求可能都查到"还有名额"，最终选课人数超过容量（超选）。

解决办法：不做先查后写，改用一条带条件的 UPDATE 语句完成扣减：

UPDATE t_course SET enrolled = enrolled + 1
WHERE id = ? AND enrolled < capacity
  • 数据库保证这条语句执行期间不会被其他语句的中间状态插入干扰（原子性）；并发的两个请求由数据库逐条排队执行，不会同时通过条件检查；
  • 影响行数为 0 说明名额已满，业务层返回 409；
  • 同一学生重复选同一门课：目前应用层与数据库都没有唯一约束拦截，这是已记录的遗留问题（见第 12.5 节）。
原子操作：要么完整执行、要么完全不执行，执行期间不受其他操作干扰。409：HTTP 状态码，表示请求与资源当前状态冲突（此处即"名额已满"）。

选课事务提交之后，缓存刷新交给第 5 章的同步链完成。数据库是唯一的数据事实来源：缓存刷新失败不影响选课结果本身，最坏情况是缓存短暂保留旧数据，直到 TTL 到期或下一次同步。

7认证设计

系统采用双令牌（Token）方案。令牌是登录成功后服务端发给客户端的凭证，之后的每次请求都携带它证明身份。

JWT（JSON Web Token）：一种自带签名和过期时间的令牌格式。服务端用密钥验证签名即可确认身份与内容，不需要查库。jti：每张令牌的唯一编号，用于精确吊销某一张令牌。BCrypt：密码的单向加密算法，数据库只存加密结果，不存明文；验证时把输入重新加密后比对。水平越权：普通用户访问另一个同级用户的数据，例如学生 A 冒充学生 B 选课。

7.1 两张令牌的分工

名称形态有效期存放位置用途
Access Token（访问令牌） JWT（HS256 签名） 30 分钟 前端内存（不写入 localStorage） 调用业务接口，放在 Authorization: Bearer 请求头
Refresh Token（刷新令牌） 随机 UUID，不含业务信息 7 天 服务端 Redis（auth:refresh:{uuid} → userId） Access 过期后换取新的一对令牌

这样分工的原因：Access 有效期短，即使泄露， 30 分钟后自动作废；Refresh 保存在服务端，管理员可以随时删除某条记录来强制下线；每次刷新时旧 Refresh 立即作废并换发新的（旋转式刷新），旧令牌被截获重放的窗口极小。

7.2 登录、请求与登出的流程

登录：校验用户名与 BCrypt 密码 → 签发 Access JWT（内容只含 userId、用户名、角色、学号、jti、过期时间）→ 向 Redis 写入 Refresh 记录
↓
业务请求：验证签名与过期时间 → 查黑名单 auth:blacklist:{jti}（已登出的令牌会被拒绝）→ 通过后进入业务逻辑；角色不足返回 403
↓ Access 过期时
刷新：客户端提交 Refresh Token → 服务端验证存在性 → 删除旧 UUID、写入新 UUID，换发新令牌对（旋转）
↓ 用户主动登出时
登出：Access 的 jti 写入黑名单（TTL 等于 Access 剩余有效期）→ 删除 Refresh 记录 → 此后旧 Access 一律 401

7.3 水平越权的收敛

选课接口的请求体只接受 courseId；studentId 一律从令牌中解析，前端传什么值都不生效。学生 A 无法操作学生 B 的数据。新增 GET /api/v1/enrollment/mine 供学生查询本人选课记录。

7.4 Redis 故障时的取舍

操作Redis 故障时的策略理由
黑名单查询fail-open：放行请求保可用。Access 本身 30 分钟过期，已登出令牌的风险窗口有上限
刷新 / 登出fail-closed：拒绝请求保安全。这两步必须写 Redis，写不进去就宁可失败，避免状态不一致
fail-open：依赖的组件故障时选择放行，保可用性。fail-closed：依赖故障时选择拒绝，保安全性。两者按操作的安全影响分别选择。

7.5 网关与应用的双层校验

网关与应用使用同一个签名密钥，各自独立验签（防御纵深：绕过网关直连应用也过不了应用这一关）。网关负责剥离外部伪造的 X-Auth-* 请求头——这类内部头只有网关验证通过后才会注入，后端只信任重新注入的值。

8可用性防护

要解决的问题：Redis 或数据库变慢、挂掉时，请求不能无限等待，故障不能扩散到整个服务。项目按四道防线处理。

8.1 第一道：全链路超时传递

每一层依赖都设置超时上限，最坏情况的等待时间可以事先算出：

环节超时说明

压测中写路径的 20 个错误正是该设计生效的表现：连接池饱和后，排队超过 3 秒的请求快速失败返回，而不是无限堆积拖垮整个服务（《测试报告》§6.3）。

8.2 第二道：Redis 熔断降级

熔断：对某个依赖的连续失败进行统计，达到阈值后暂时停止调用它，直接走备用路径，避免每个请求都白白等待超时。降级：熔断期间的备用处理方式，用功能换可用。半开：熔断打开一段时间后放行少量请求试探依赖是否恢复，据此决定关闭或继续熔断。

熔断由 Resilience4j 实现，参数：统计窗口 50 次调用（至少 10 次才判定）、失败率 ≥50% 或慢调用（超过 300ms）占比 ≥80% 时打开；打开期间不再访问 Redis；10 秒后进入半开，放行 2 次探测，成功则关闭，失败则重新打开。

CLOSED正常状态，调用放行，持续统计失败率
失败率 ≥50%
或慢调用占比 ≥80%
OPEN跳过 Redis，读直接查数据库，写跳过缓存写入
等待 10 秒
HALF_OPEN放行 2 次探测请求

探测成功 → 回到 CLOSED；探测失败 → 回到 OPEN。

降级时的具体行为

操作降级行为依据
读缓存（get）返回空 → 读路径直接查 MySQL数据库是事实来源，功能不中断
写缓存（put）跳过已提交的数据库数据不受影响，缓存等 TTL 到期或下次同步恢复
删缓存（delete）重试 1 次后跳过旧缓存最长存活到自身 TTL 到期，此取舍已记录

故障演练的实测数据（《测试报告》§三）

场景观测结果
Redis 挂起（连接黑洞），首个未命中请求3.4 秒（建连与命令超时的有界代价）
熔断打开后同路径延迟降到 7~8 毫秒（对比无熔断时的 60 秒级挂起）
故障期间 15 个同键并发请求数据库回源仅 1 次（防击穿生效，见 8.3）
故障期间提交选课成功，256 毫秒（写路径不受影响）
故障恢复（黑洞换成真实 Redis 的转发器）10 秒后半开探测成功，2 次探测后关闭；L2 重新回填（8 毫秒命中）

8.3 第三道：缓存击穿防护（两级）

击穿：某个热点缓存键失效的瞬间，大量并发请求同时发现缓存为空，一起去查数据库，瞬时压力全部落到数据库。

两级防护把"同键的 N 个并发回源"压缩成 1 次实际数据库查询：

  1. 进程内单飞（SingleFlight）：同一进程内，相同键的并发请求只放行一个去查数据库，其余等待它把结果写回缓存后直接取用；等待预算 6 秒，超时按失败处理且不缓存失败结果。
  2. 分布式回源锁（CacheLoadLock）：多实例部署时，跨进程用 Redis 锁保证同一键同一时刻只有一个实例回源。加锁用 SET NX PX，释放时用 Lua 脚本校验持锁者身份再删除，防止误删他人的锁；Redis 异常时一律按"没抢到锁"处理，退化为允许回源（可用性优先）。
SET NX：Redis 的"键不存在才写入"命令，天然适合做互斥锁。Lua 脚本：Redis 支持的一小段原子执行的脚本，保证"检查 + 删除"两步不可拆分。

8.4 第四道：防护状态本身可观测

Redis 降级次数（hercules_cache_redis_degraded）与熔断状态（hercules_cache_redis_circuit_state）都作为指标暴露，运行期可以随时确认防护是否触发、当前处于哪个状态。

9日志与可观测

traceId：一次请求的唯一编号。它出现在这条请求产生的每一行日志里，把分散在网关、应用、同步链多个环节的日志串起来，故障时按编号检索即可还原完整路径。

9.1 traceId 的贯通路径

1网关：取上游请求头中的 X-Trace-Id（有则复用），没有则生成 16 位短 ID
↓
2网关：ID 写入转发给应用的请求头，同时写入返回给客户端的响应头
↓
3应用：过滤器（最高优先级，先于安全链执行）从请求头取出 ID，写入日志上下文 MDC
↓
4此后该线程的每行日志自动携带 ID（日志格式中的 %X{traceId}）；事务提交后的同步链消费在同一线程执行，日志同样携带
MDC：日志框架提供的"按线程存放上下文"的机制，配置一次输出格式，线程内所有日志自动带上。

9.2 日志文件布局

通道文件与滚动策略内容
控制台 + 主日志 按天且按 100MB 滚动，保留 30 天或 1~2GB，UTF-8 显式声明 常规业务日志，经异步输出
认证审计（独立文件 auth-audit.log，保留 90 天） 独立滚动，独立保留期 登录成功 / 登录失败（记录用户名、IP、失败原因，不含密码）/ 登出 / 黑名单拒绝

主日志经异步输出：日志先进入容量 4096 的内存队列，由独立线程写盘。高并发（如压测）时日志写入不阻塞业务线程；容器环境挂载持久卷，重启不丢日志。

9.3 指标出口

  • hercules_cache_*：L1/L2 命中与未命中、数据库回源、Redis 降级、熔断状态；

  • 全部经 /actuator/prometheus 暴露；Grafana 的大盘（8 个面板：应用与网关 QPS、P95/P99 延迟、错误率、缓存命中、同步链、熔断状态、JVM 堆、线程池）实时显示。

13.3 状态管理与数据流

Pinia 按领域分片五个 store：auth（令牌/档案）、course（列表/详情）、enrollment（选课/退课）、monitor（统计快照 + 轮询采样）、chat（消息流式状态机）。严格单向数据流：组件只读 state，写操作一律经 action 调用 api 层；R<T> 解包发生在 api 层；跨 store 依赖单向（enrollment → course）。

认证存储策略：accessToken 仅内存（不落 localStorage，缩小 XSS 窗口），refreshToken 存 localStorage（7 天，服务端可吊销）；页面刷新后经 401 静默刷新恢复会话——单飞语义保证并发请求只触发一次刷新，失败统一跳登录（Vitest 覆盖）。

13.4 对话链路（前后端契约）

1前端 POST /api/v1/chat（sessionId + message），响应用 SSE 分片推送
↓
2token 事件逐片到达 → 追加到最后一条 assistant 消息（流式渲染）
↓
3meta 事件（候选课程 + 冲突标注 / 选课校验结果）→ 渲染候选卡与操作按钮
↓
4流结束：助手全文入会话历史；error 事件兜底（LLM 故障已在后端降级为候选列表）

自研 SSE 解析器处理跨 chunk 粘包、多行 data 与 CRLF（15 个 Vitest 用例之一）；生成可随时中断（AbortController）。
