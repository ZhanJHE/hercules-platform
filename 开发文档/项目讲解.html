Hercules 项目讲解

这个项目要解决的问题是：课程数据被很多人在读，同时还被不断修改，缓存和数据库之间怎么保持一致。下面先讲代码长什么样，再讲一个请求进来之后，一路都发生了什么。

一、整体是怎么分层的

从上到下四层。每一层只干自己的事，越往下越靠近数据。

第一层　接入

浏览器Vue 3 前端，学生端和管理端共用一个布局
网关 :8081验签、注入用户信息、生成 traceId
↓

第二层　应用

hercules-application :8080所有对外的接口、安全配置、对话入口
hercules-agent四个智能体，需要时会调智谱大模型
↓

第三层　一致性处理

hercules-cache两级缓存、熔断、防止同时回源
hercules-sync给变更打版本号、判断新旧、合并冲突
hercules-inspector巡检与自愈
↓

第四层　存储

MySQL 8业务数据，开着 Row 格式的 Binlog
Redis二级缓存，以及令牌的白名单和黑名单
Milvus + Neo4j做 RAG 检索用
这一层结构里，hercules-agent 不直接依赖 hercules-application。它需要什么业务能力，就在自己的 port/ 包里声明接口，由应用层实现。这样依赖方向是单向的，不会绕成死循环。

二、代码分成哪些模块

一个 Maven 工程，按职责拆成多个模块。前端是独立的 npm 工程，不参与 Java 依赖。

模块里面是什么状态
hercules-common实体、异常、JSON 工具、缓存键的拼法、Mapper已完成
hercules-cache两级缓存的主逻辑、过期时间策略、熔断、防止击穿已完成
hercules-sync向量时钟、版本消息的生产与消费、字段级合并、Binlog 消费已完成
hercules-agent路由、推荐、排课、执行四个智能体和编排器已完成
hercules-gateway独立进程的网关，只有验签和透传几个类已完成
hercules-application唯一能启动的模块：接口、安全、对话、种子数据已完成
hercules-inspector巡检与自愈空模块
hercules-rag检索课程大纲、评价这类文字资料空模块
hercules-observability可观测性聚合空模块
hercules-admin管控台后端空模块
hercules-uiVue 3 前端已完成
loadtestJMeter 压测工程已完成
deploy十个容器的编排和配置已完成

依赖方向

common ← cache ← sync ← agent ← application

箭头从右往左。左边的模块不知道右边的模块存在。网关和前端是独立进程，只通过 HTTP 打交道。

三、数据存在哪里

MySQL 的表

表存什么
t_course课程。容量 capacity 和已选人数 enrolled 是防超选的关键；上课时间和先修课用 JSON 文本列存
t_enrollment选课记录。(student_id, course_id) 上有唯一键，同一个学生同一门课只能有一行；status 为 2 表示已退选
t_user用户。密码用 BCrypt 存，角色是学生或管理员
t_cache_version每个缓存键当前的最新版本号（向量时钟），用来判断新旧
t_agent_trace智能体每次干活都写一条：用的哪个模型、花了多少毫秒、成功还是失败
t_repair_log表建了，没有代码用它（巡检没做）

Redis 里存什么

键过期时间存什么
course:{id}300 秒课程详情。这个键参与后面的版本机制
course:list:{页}:{条数}:{关键字}10 秒课程列表。不进版本机制，靠 10 秒过期兜底
auth:refresh:{uuid}7 天刷新令牌的白名单，用一次换一次
auth:blacklist:{jti}等于 accessToken 剩余有效时间登出黑名单
回源锁3 秒防止多个实例同时查数据库
进程内还有一级缓存（Caffeine），不落盘、不共享。详情键活 60 秒，列表键活 10 秒。

四、请求一：查课程（读）

接口 GET /api/v1/courses?page=1&size=10。调用链是 CourseController.list → CourseService.list。

  1. 网关先看这个请求能不能进 验签、看令牌过没过期，然后把用户信息塞进请求头，交给应用。
  2. 应用再验一次，然后按角色判断权限 课程查询只要登录就行，不需要管理员。
  3. 拼出缓存键 CacheKeys.courseList(page, size, keyword)。关键字会先去掉首尾空格并转成小写，所以 "Java" 和 "java" 是同一个键。
  4. 查一级缓存（进程内的 Caffeine） 命中就直接返回，数据库一个字节都不用碰。列表键活 10 秒。
  5. 没命中，查二级缓存（Redis） 命中就返回，顺手把结果塞回一级缓存，下次更快。
  6. 还没有，才去查数据库 这里有两道闸：先看有没有别的线程正在查同一个键（有就等它的结果，不重复查），再抢一把 Redis 上的分布式锁（防止另一个实例也在查）。抢不到锁就每 50 毫秒瞄一眼二级缓存，最多等 2 秒；还等不到就自己查——宁可多查一次，也不能让请求一直卡着。
  7. 查到结果，往两级缓存回填，然后返回 先写 Redis，再写本地缓存。查不到（课程不存在）就不缓存，直接返回空，由接口返回 404。
Redis 挂掉会怎样？熔断器打开，直接跳过二级缓存去查数据库，请求不会被拖住。等 Redis 恢复，熔断器半开探测成功后再自动恢复使用。

五、请求二：选课（写）

接口 POST /api/v1/enrollment，请求体只有 courseId。谁在选课不由前端说了算，而是从令牌里取。

  1. 从令牌里取学号，并且必须是学生 EnrollmentService.requireStudentId。前端传什么都不作数，避免学生改个参数就能替别人选课。
  2. 先看有没有重复选课 已经选过、状态是已选的，直接返回 409，不往下走。
  3. 用一条带条件的更新语句扣人数 关键就在这条语句：
    UPDATE t_course SET enrolled = enrolled + 1 WHERE id = ? AND enrolled < capacity
    课程已经满了，这条语句就影响 0 行，接口返回 409。判断有没有超员和扣人数是同一条语句完成的，中间没有空隙，所以并发点也不会超选。
  4. 写选课记录 如果这个学生以前退过这门课，就把原来那行改回已选（复活），而不是新插一行；否则新插一行。两种冲突都由数据库的唯一键兜底，撞上了还是返回 409。
  5. 事务提交 到这一步数据库里才算真的改了。
  6. 提交之后，才发一条「数据变了」的消息 顺序很重要：先提交、后同步。如果事务回滚了，消息根本不会发出去，缓存也就不会变成错的值。这一步由 @TransactionalEventListener 挂在提交事件上完成。
  7. 消息被消费者接住，去刷新缓存 消费者拿新版本和数据库里存的旧版本比，决定是用新值刷新、还是丢掉、还是合并。这段见第八节。
消息有两条路，由配置项 hercules.sync.transport 决定：
· in-process（本机跑和测试用）：上面第 6 步直接在本进程里发事件。
· canal-mq（容器部署用）：业务代码在第 5 步就结束了，不再发消息、也不再重读数据库。刷新的触发源变成 MySQL 的 Binlog：Canal 读到变更 → 投给 RocketMQ → 应用消费。好处是写请求更快，而且别人绕开应用直接改数据库，缓存也会跟着更新（实测 250 毫秒）。

六、请求三：登录与鉴权

登录发两个令牌，一个管当前操作，一个管续期。之后每个请求都要带着第一个。

登录时发生了什么

  1. 查用户，用 BCrypt 比对密码 AuthController.login。密码在数据库里是加密存的，比对的是哈希，不是原文。
  2. 签发两个令牌 accessToken 是一个 JWT，30 分钟有效，里面写着用户是谁、什么角色；refreshToken 是一个随机字符串，7 天有效。
  3. 把 refreshToken 记进 Redis 白名单 只有在这个白名单里的刷新令牌才认。用一次就换成新的、旧的作废，所以刷新令牌即使被偷也只能用一次。

之后每个请求怎么鉴权

前端：accessToken 只放在内存里，不写 localStorage（减少被脚本偷走的机会）；refreshToken 放 localStorage。页面刷新后靠 401 自动静默续期一次，续不上就跳登录页。

网关：验签、看过期；把客户端伪造的 X-Auth-* 请求头先删掉，再注入可信的用户信息，然后转发。（网关这里不查登出黑名单）

应用：再验一次签，并且查黑名单，然后按角色判断这个路径能不能访问。拒绝时统一返回 401 或 403 的 JSON。

登出：refreshToken 从白名单删掉，accessToken 的身份标识进黑名单，剩下的有效期内也不能再用。

七、请求四：用对话选课

接口 POST /api/v1/chat，返回的不是普通 JSON，而是流式一段一段推回来，前端边收边显示。

  1. 先确认这个会话是你自己的 会话号第一次使用时就和当前用户绑定。别人猜到你的会话号也用不了，会返回 403——否则就能偷看你的聊天记录、甚至替你确认选课。
  2. 判断你想干什么 RoutingAgent 先用关键词判断：说「确认」是确认，说「帮我选」是选课，其他都当推荐。关键词判断不出来时才去问大模型；大模型那边出问题就退回按推荐处理，不会卡住。
  3. 走对应的链 · 推荐：RecommendationAgent 先查出候选课程，逐门标出和时间冲突、先修课不满足的情况，再让大模型写一段推荐理由，边生成边推给前端。
    · 选课：SchedulingAgent 只用规则算——上课时间有没有重叠、先修课选了没有、学分一共多少。这一段完全不问大模型，所以计算是 0 秒、结果是确定的。
  4. 选课不直接执行，先要你确认 校验通过后只是把「待选课程」记在会话里，回一句「请回复确认」。你说确认之后，ExecutionAgent 才真正去调用选课逻辑，而且再查一次是不是学生。大模型没有直接写数据库的权限，所有写操作都走和普通选课完全一样的路径，防超选那套保护照样生效。
  5. 边推边记，最后收尾 正文用 token 事件一段段推；候选课程和冲突信息用 meta 事件单独发，前端拿它渲染成卡片和按钮；每一步都往 t_agent_trace 写一条记录（用了哪个模型、耗时多少、成功没有）。
大模型挂了会怎样？不会出报错页。问答会退化成一份结构化的候选课程列表，用户照样能看到有什么课、点按钮自己选。实测从发起请求到拿到降级结果是 1 秒。

八、数据改了，缓存怎么跟着变

这是整个项目的核心。要解决两件事：缓存怎么自动更新；两个节点同时改同一条数据时，谁说了算。

第一步：给每次变更打一个版本号

每次数据变更，都生成一条带版本号的消息。这个版本号叫向量时钟，样子是一个小表，比如 {"node-1": 3, "node-sim": 1}，意思是「node-1 这个节点改过 3 次，node-sim 改过 1 次」。生成规则是：读出数据库里存的旧时钟，然后把自己这一项加一。

第二步：消费者拿新旧版本比一比

比较结果只有三种，处理方式各不相同：

比较结果说明与处理
新的比旧的更新 正常情况。用新值刷新二级缓存、清掉一级缓存、把新版本号存进版本表。
一样，或者更旧 说明这条消息是重复投递或者迟到的。直接丢掉，不重复处理——消息中间件保证不了只投一次，靠这一步做到重复投递也没关系。
两边互有大小 说明两个节点各改各的，谁都没看到对方的修改，这叫并发冲突。这时不能简单用新的覆盖旧的，那会丢掉另一边的改动。做法是逐字段比时间戳：同一个字段谁的时间新用谁的，两边各自独有的字段都保留。最后把两边的版本号合并成一个存回去，并给这次冲突记一笔。
为什么不能只看时间戳？因为不同机器的时钟可能对不齐，光比时间戳会误判。向量时钟比的是「改动之间的因果关系」——只有当一方确实看过另一方的改动、并在它基础上继续改，才叫更新；两边互相没看过，就叫并发。

第三步：列表数据为什么不跟着一起变

课程列表没有被纳入这套版本机制。原因是列表的组合太多了（不同页码、不同关键字都是不同的键），逐个失效成本很高。所以列表只给 10 秒过期时间：选课之后，最迟 10 秒后列表里的已选人数就会变成新的。

九、哪些东西没做

下面这些在开工文档里写了，但代码里确实没有。写论文和答辩时不要当成已完成。

没做的影响
巡检引擎（hercules-inspector 是空模块） 缓存和数据库万一真出现不一致，没有检测手段；另外消费者是从消息队列最新位置开始读的，应用启动之前发生的数据变更不会被补刷。这两件事本来都指望它兜底。
eBPF 采集 原计划用 Grafana Beyla 不改代码就采到指标，实际用的是 Micrometer 手工埋点。这一条在开工文档里标的是 P0。
分布式链路追踪 现在只有一个 traceId 写在日志里，能按它把同一个请求的日志串起来，但没有各段耗时拆解，算不上链路追踪。
一致性健康度评分 没有这个指标，监控大盘上看不到「缓存和数据库现在有多一致」。
RAG 检索（hercules-rag 是空模块） 推荐理由只能基于课程名、学分、老师、上课时间这些结构化字段，用不上课程大纲、评价这类文字资料。
压测结论要重测 现有性能数字是 2026-09-07 测的。之后加了选课唯一键、把写路径改成 Binlog 异步、加了智能体和前端，口径已经变了，老数字不能直接引用。
智能体动态注册、队列积压监控、多节点部署验证 四个智能体是写死在编排器里的；消息队列有没有积压看不到；应用是单实例部署，没做过某个节点挂掉的验证。
