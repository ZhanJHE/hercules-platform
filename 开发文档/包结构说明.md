## 一、整体包结构树（实际形态：Maven 多模块，2026-09-10 核实）

```
hercules-platform/
├── hercules-common/               # 公共基础 ✅：模型（含 agent/sync）、异常、JSON 工具、Mapper
├── hercules-cache/                # 缓存治理 ✅：多级缓存、TTL 策略、熔断/防击穿、命中统计
├── hercules-sync/                 # 数据同步 ✅：向量时钟、Canal+RocketMQ 消费、LWW 合并
├── hercules-agent/                # 多智能体 ✅（阶段 D）：四类智能体 + Spring AI 接入
├── hercules-gateway/              # API 网关 ✅（阶段 H-2，独立进程）：JWT 验签、透传头、traceId
├── hercules-application/          # 唯一可执行聚合 ✅：REST、安全、SSE 对话、适配器、种子
├── hercules-inspector/            # 巡检引擎（空模块，阶段 C 顺延）
├── hercules-rag/                  # RAG 检索（空模块，阶段 E）
├── hercules-observability/        # 可观测性聚合（空模块，阶段 F）
├── hercules-admin/                # 管控台后端（空模块，规划）
├── hercules-ui/                   # Vue3 前端 ✅（阶段 G，npm 工程，nginx 容器 :8090）
├── loadtest/                      # JMeter 压测工程 ✅（阶段 H-4）
└── deploy/                        # Docker Compose 十容器编排 + canal/rocketmq/ui 配置 ✅
```

> **多模块化已于「阶段 A」落地**：工程 `hercules-platform/`（11 个 Maven 模块），
> 原单模块代码按包 1:1 平移（common→hercules-common、cache→hercules-cache、sync→hercules-sync、
> service/controller/config→hercules-application，GlobalExceptionHandler 调整为 `web` 包），
> 空占位模块（inspector/rag/agent/observability/admin/gateway）按后续阶段填充。
> 单模块形态的历史见 git 基线提交 `bfb4b6e`。阶段 B/D/G 已填充 sync/agent/gateway/ui 并配套
> `loadtest/`、`deploy/`（十容器编排），依赖矩阵见本文 §三（按实际代码核实）。

## 二、逐模块详细注释

### 1. hercules-common —— 公共基础模块

全平台的公共基座：领域模型、常量、枚举、异常与工具类。所有模块仅向下依赖本模块，不允许反向依赖。

| 类 | 详细说明 | 状态 |
| :--- | :--- | :--- |
| `model/clock/VectorClock` | 向量时钟：`(nodeId → counter)` 分量 TreeMap，提供 `increment`（本节点自增）、`merge`（逐分量取 max）、`compare`（AFTER/BEFORE/EQUAL/CONCURRENT 判定）、`isConcurrent`；写操作 `synchronized` 保护；序列化为 JSON 存入 `t_cache_version.vector_clock_json`。是 FR-HC-03 冲突消解的核心算法类。 | ✅ 实现于 `sync.clock` |
| `model/clock/VersionedValue` | 携带向量时钟的版本化值：缓存键 + 值 JSON + 产生节点 + 时间戳（LWW 裁决依据）+ 时钟；同步链路统一载荷。 | ✅ 实现于 `sync.model`（record） |
| `model/cache/CacheKey` | 缓存键构建器（前缀 + 业务 ID + 后缀），统一键命名。 | 🔄 由 `common.CacheKeys` 静态工具承担 |
| `model/sync/BinlogEntry` | Binlog 事件模型：库表名、变更类型、行数据（列名 → 字符串值 Map）、事件执行时间、binlog 位点；canal flatMessage 的解析中间层。 | ✅ 阶段 B |
| `model/sync/ChangeType` | 变更类型枚举 INSERT / UPDATE / DELETE。 | ✅ 阶段 B |
| `model/agent/AgentContext` | 智能体执行上下文：sessionId、traceId、userId/studentId/role（取自 JWT）、本轮消息、多轮历史；`isStudent()` 供执行智能体前置校验。 | ✅ 阶段 D |
| `model/agent/AgentResult` | 智能体执行结果：智能体类型、成功标记、文本内容、结构化附加数据、失败原因。 | ✅ 阶段 D |
| `model/agent/ChatTurn` | 多轮对话单条发言（user/assistant）。 | ✅ 阶段 D |
| `model/AgentTrace` + `mapper/AgentTraceMapper` | 智能体调用记录实体与 Mapper ↔ `t_agent_trace`（阶段 D 启用，BaseAgent 语义由 AgentTraceWriter 承担）。 | ✅ 阶段 D |
| `model/enrollment/Course` | 课程实体 ↔ `t_course`（课程编码唯一，容量/已选数、上课时间与先修课 JSON 列——MVP 以 TEXT 承载）。 | ✅ 实现于 `model.Course` |

| `model/enrollment/Enrollment` | 选课记录实体 ↔ `t_enrollment`；`status` 取值 0-预选 / 1-已选 / 2-退选。 | ✅ 实现于 `model.Enrollment` |
| `model/inspection/ConsistencyDiff` | 巡检差异数据：缓存键、DB/缓存双端值、时间戳、滞后毫秒、冲突类型。 | ⏳ Sprint 4 |
| `constant/CacheConstants` | 缓存键前缀、TTL、 topics 等常量。 | 🔄 由 `common.CacheKeys` + 配置项承担 |

| `constant/SystemConstants` | 系统级常量（节点名、日期格式等）。 | ⏳ 按需 |
| `enums/ConflictType` | 冲突类型：VERSION_CONFLICT / DATA_LOST / DATA_MISMATCH / NONE。 | ⏳ Sprint 4（巡检用） |
| `enums/RepairStatus` | 修复状态：PENDING / AUTO_FIXED / MANUAL_REQUIRED / FAILED，对应 `t_repair_log.repair_status`。 | ⏳ Sprint 4 |

### 2. hercules-cache —— 缓存治理模块（门面模式 + 策略模式）

多级缓存统一入口：L1 Caffeine（进程内）→ L2 Redis（分布式）→ MySQL，cache-aside 读路径逐级回填；写路径配合同步链失效/刷新。

| 类 | 详细说明 | 状态 |
| :--- | :--- | :--- |
| `core/CacheManager` | 缓存门面接口：`get(key, loader)` cache-aside 读取、`put`、`invalidate`（双级失效）、`invalidateLocal`（仅 L1，演示回填用）；值统一以 JSON 字符串承载。 | ✅ 实现于 `cache.core` |
| `core/MultiLevelCacheManager` | 多级缓存实现：L1 命中→返回；L1 未命中查 L2，命中回填 L1；L2 未命中执行 loader 查 DB 并回填两级。每级路径打点命中率统计；L2 允许缺省（无 Redis 环境退化为 L1+DB）。 | ✅ 实现于 `cache.core` |
| `core/LocalCacheManager` | 本地缓存抽象接口：get/put/invalidate/estimatedSize。 | ✅ 实现于 `cache.local` |
| `core/DistributedCacheManager` | 分布式缓存抽象接口：get/put(含 TTL)/delete。 | ✅ 实现于 `cache.remote` |
| `strategy/TTLStrategy` | TTL 策略接口：按键区分详情键/列表键的本地与远端 TTL。 | ✅ 实现于 `cache.strategy` |
| `strategy/FixedTTLStrategy` | 固定 TTL 实现：列表键（前缀 `course:list:`）10s 最终一致窗口；详情键 L1 60s / L2 300s。 | ✅ 实现于 `cache.strategy` |
| `strategy/AdaptiveTTLStrategy` | 自适应 TTL：按访问频次动态调整（热点键延长、冷键缩短）。 | ⏳ 后续冲刺 |
| `strategy/EvictionStrategy` | 淘汰策略扩展点。 | ⏳（MVP 由 Caffeine 内置 W-TinyLFU 承担） |
| `stats/CacheStatsCollector` | 运行时计数器：L1/L2 命中与未命中、DB 回源、版本应用数、冲突检测数（AtomicLong）；`bindTo(MeterRegistry)` 注册为 Micrometer FunctionCounter（`hercules.cache.*` / `hercules.sync.*` 指标族）；`snapshot()` 计算总体命中率 = (L1 命中+L2 命中)/总读请求。 | ✅ 实现于 `cache.stats` |
| `stats/CacheHitRateCalculator` | 命中率计算器。 | 🔄 语义并入 `snapshot().cacheHitRate()` |
| `config/CaffeineConfig` | Caffeine 装配：expireAfterWrite 全局固定 TTL + maximumSize + recordStats。 | ✅ 并入 `CacheConfig` + `CaffeineLocalCacheManager` |
| `config/RedisConfig` | Redis 装配。 | 🔄 Boot 自动装配 `StringRedisTemplate`（Lettuce）+ `RedisDistributedCacheManager` |

### 3. hercules-sync —— 数据同步模块（观察者模式 + 策略模式）★核心

缓存一致性同步链：Binlog 事件 → 版本化消息 → 向量时钟消费者（新版本应用 / 旧版本幂等丢弃 / 并发冲突合并）→ 刷新缓存与版本表。

| 类 | 详细说明 | 状态 |
| :--- | :--- | :--- |
| `listener/BinlogEventListener` | Binlog 监听器接口：start/stop/onBinlogEvent。 | 🔄 未按接口落地——canal-mq 模式由 `RocketMQBinlogListener`（SmartLifecycle）承担 |
| `listener/CanalBinlogListener` | Canal 实现：伪装 MySQL Slave 拉取 Binlog，转换为 BinlogEntry。 | 🔄 形态调整——canal server 以 MQ 模式直接投递 RocketMQ，应用侧 `listener/RocketMQBinlogListener` 仅消费 MQ（不依赖 canal client），✅ 阶段 B |
| `producer/VersionChangeProducer` | 版本变更生产者接口：`publish(VersionedValue)`；调用契约——业务事务内落库后调用，实现不得因传输异常中断业务事务。 | ✅ 接口实现于 `sync.producer` |
| `producer/InProcessEventBusProducer` | **进程内事件总线**（文档树外补充）：Spring 进程内事件总线；事件由监听器在 AFTER_COMMIT 消费，保证「先提交、后同步」。 | ✅（默认传输 `transport=in-process`；canal-mq 模式下保留，供演示钩子使用） |
| `listener/VersionChangeEventListener` | **MVP 事务桥**（文档树外补充）：`@TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true)`——有事务则提交后消费，无事务（调试端点）立即消费；异常捕获记日志，不影响已提交业务。 | ✅ |
| `model/VersionChangeEvent` | **MVP 事件信封**（文档树外补充）：包裹 VersionedValue；Sprint 2 更换传输层后载荷结构不变。 | ✅ |
| `consumer/VersionChangeConsumer` | 版本变更消费者（含 VersionConflictResolver 语义）。决策表：比对 `t_cache_version` 存量时钟——AFTER 应用（写 L2 → 失效 L1 → upsert 版本记录）；EQUAL/BEFORE 丢弃（幂等）；CONCURRENT 字段级 LWW 合并后应用并记冲突。应用/冲突分别计数并暴露 Micrometer 指标。 | ✅ 实现于 `sync.consumer` |
| `consumer/VersionConflictResolver` | 冲突消解器。 | 🔄 语义并入 Consumer + ConflictMergeStrategy |
| `consumer/RepairTaskConsumer` | 修复任务消费者：执行巡检产生的补偿任务，更新 `t_repair_log`。 | ⏳ Sprint 4 |
| `processor/BinlogMessageProcessor` | Binlog 消息处理器接口（监听器→生产者之间的处理管道）。 | 🔄 语义并入 `BinlogToVersionConverter`（过滤 + 转换合一） |
| `processor/DefaultBinlogProcessor` | 默认实现：过滤关注表 → 转版本化值 → 发送。 | 🔄 同上 |
| `convert/BinlogToVersionConverter` | BinlogEntry → VersionedValue 转换器（含向量时钟构建：存量 ⊕ node-id 自增，时间戳取 binlog es），输出直交 `VersionChangeConsumer`。 | ✅ 阶段 B |
| `convert/MySQLTypeMapper` | MySQL 类型 → Java 类型映射（JSON 列、DATETIME(3) 等）。 | 🔄 由 `convert/CourseRowMapper` 承担（t_course 单表行映射、宽松解析） |
| `listener/RocketMQBinlogListener` | **阶段 B 新增**：canal-mq 模式专属 Bean（SyncConfig 按条件装配）；封装 `DefaultMQPushConsumer` 顺序消费（消费线程 1），flatMessage JSON → 转换器；异常挂起队列重试、毒消息跳过。 | ✅ 阶段 B |
| `producer/NoopVersionChangeProducer` | **阶段 B 新增**：canal-mq 模式下业务写路径的 `@Primary` 注入点（事务内发布失效，同步触发源移交 binlog 链路）。 | ✅ 阶段 B |
| `producer/RepairTaskProducer` | 修复任务生产者：巡检差异 → 修复队列。 | ⏳ Sprint 4 |
| `support/VersionReader` | **MVP 辅助**（文档树外补充）：读取缓存键的存量版本记录/向量时钟；供生产者构建 incoming 时钟（存量 ⊕ 本节点自增）与调试端点判断冲突前置。 | ✅ |

## 三、模块依赖矩阵（按实际代码核实，2026-09-10）

| 来源模块 | 目标模块 | 依赖关系 | 原因 |
| :--- | :--- | :--- | :--- |
| hercules-cache | hercules-common | 编译依赖 | 实体、异常、CacheKeys、JsonUtil |
| hercules-sync | hercules-common | 编译依赖 | BinlogEntry、VectorClock、CacheVersion 等模型 |
| hercules-sync | hercules-cache | 编译依赖 | 消费端经 CacheManager/DistributedCacheManager 刷新缓存 |
| hercules-agent | hercules-common | 编译依赖 | AgentContext/Result、AgentTrace、Spring AI 客户端 |
| hercules-agent | （Spring AI） | 编译依赖 | spring-ai-starter-model-openai（GLM OpenAI 兼容接入） |
| hercules-application | common/cache/sync/agent | 编译依赖 | 聚合启动 + AgentPortAdapter 适配 agent 端口 |
| hercules-gateway | （独立进程） | 无代码依赖 | 仅与 application 共享 JWT 签名密钥（双层验签） |
| hercules-ui | （独立 npm 工程） | HTTP 契约依赖 | 经网关消费 R<T> 接口与 SSE，反代同源无 CORS |

> 端口反转说明：agent 模块经 `port/CourseQueryPort/EnrollmentPort` 声明业务能力，
> application 的 `adapter/AgentPortAdapter` 提供实现——依赖单向无环（依赖矩阵原规划中
> "gateway→agent" 等条目随实际形态作废）。

## 四、MVP 实现映射（单模块 → 目标多模块）

MVP 在 `hercules/src/main/java/com/zhanjh/hercules` 下按目标模块同构分包，拆分时按包平移即可：

| 目标模块 | MVP 包 | 内容 |
| :--- | :--- | :--- |
| hercules-common | `common` / `model` / `mapper` | R、BusinessException、JsonUtil、CacheKeys、PageResult、Course/Enrollment/CacheVersion、三个 Mapper |
| hercules-cache | `cache.*` | MultiLevelCacheManager、Caffeine/Redis 实现、TTL 策略、统计、装配 |
| hercules-sync | `sync.*` | VectorClock、VersionedValue、生产者/监听器/消费者、FieldLwwMergeStrategy、VersionReader |
| hercules-gateway（API 部分） | `controller` | Course/Enrollment/CacheStats/Debug 四个 Controller |
| hercules-observability（指标部分） | `cache.stats` + actuator | Micrometer 指标 + `/actuator/prometheus` |
| hercules-application | `HerculesApplication` | 启动类 |
| inspector / agent / rag / admin / ui | — | ⏳ 按冲刺计划实现 |
