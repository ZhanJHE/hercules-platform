# 包结构说明

这份文件说明项目里每个包和类实际是干什么的，以代码为准。核对日期：2026-09-11。

- 这份文件只管代码结构。设计意图和取舍看[设计说明.md](设计说明.md)，需求做到哪一步看[路线图.md](路线图.md)。
- 状态一列的含义：已完成 = 代码里有；已实现（形态不同）= 做了，但和原设计不一样；未实现 = 代码里没有。
- 哪些模块整个是空的，见本文第五节。

---

## 一、整体包结构树

```
hercules-platform/
├── hercules-common/               # 已完成：实体、异常、JSON 工具、Mapper
├── hercules-cache/                # 已完成：多级缓存、TTL 策略、熔断与防击穿、命中统计
├── hercules-sync/                 # 已完成：向量时钟、Binlog 消费、字段级合并
├── hercules-agent/                # 已完成：四个智能体 + Spring AI 接入
├── hercules-gateway/              # 已完成：独立进程的网关，验签、透传头、traceId
├── hercules-application/          # 已完成：唯一可执行的模块，接口、安全、SSE、种子数据
├── hercules-inspector/            # 空模块，没有任何代码
├── hercules-rag/                  # 空模块，没有任何代码
├── hercules-observability/        # 空模块，没有任何代码
├── hercules-admin/                # 空模块，没有任何代码
├── hercules-ui/                   # 已完成：Vue3 前端，npm 工程，nginx 容器跑在 8090
├── loadtest/                      # 已完成：JMeter 压测工程
└── deploy/                        # 已完成：十个容器的编排，以及 canal、rocketmq、ui 的配置
```

拆分过程：工程原来是一个 Maven 模块，阶段 A 拆成多模块，代码按包 1:1 平移（`common`→hercules-common、`cache`→hercules-cache、`sync`→hercules-sync、`service`/`controller`/`config`→hercules-application，`GlobalExceptionHandler` 挪到 `web` 包）。单模块时期的样子见 git 提交 `bfb4b6e`。空模块里的 agent、gateway 后来在阶段 D、H 填上了，sync 和 ui 也已就位。

### 2. hercules-cache —— 多级缓存

| `core/LocalCacheManager` | 一级缓存的接口 | 已完成 |

### 3. hercules-sync —— 数据同步

项目的核心之一。链路是：Binlog 事件 → 带版本的消息 → 消费者比对版本（新的就用、旧的丢掉、并发就按字段合并）→ 刷新缓存和版本表。

| 类 | 说明 | 状态 |
| :--- | :--- | :--- |
| `listener/BinlogEventListener` | Binlog 监听器接口 | 未实现（canal-mq 模式下由 `RocketMQBinlogListener` 承担） |
| `listener/CanalBinlogListener` | 假装成 MySQL 从库拉 Binlog | 已实现（形态不同）：Canal 以 MQ 模式把消息投到 RocketMQ，应用侧只消费 MQ，不用 canal 客户端。阶段 B 完成 |
| `producer/VersionChangeProducer` | 版本变更发送接口。约定：业务事务里落库后调用，发送失败不能影响业务事务 | 已完成 |
| `producer/InProcessEventBusProducer` | 进程内发事件。由监听器在事务提交后消费，保证先提交后同步 | 已完成（默认传输 `transport=in-process`；canal-mq 模式下保留，给演示用） |
| `listener/VersionChangeEventListener` | 事务桥。`@TransactionalEventListener(AFTER_COMMIT)`：有事务就等提交后消费，没有事务（调试接口）立刻消费。异常只记日志，不影响已经提交的业务 | 已完成 |
| `model/VersionChangeEvent` | 事件信封，里面装 VersionedValue | 已完成 |
| `consumer/VersionChangeConsumer` | 消费者。拿消息的时钟和 `t_cache_version` 里存的时钟比：新的就用（写二级缓存、清一级缓存、更新版本记录）；一样或更旧就丢掉；并发就按字段合并后使用，并记一次冲突 | 已完成 |
| `consumer/VersionConflictResolver` | 冲突消解器 | 已实现（形态不同）：并入消费者和 `FieldLwwMergeStrategy` |
| `consumer/RepairTaskConsumer` | 消费巡检产生的修复任务，写 `t_repair_log` | 未实现 |
| `processor/BinlogMessageProcessor` | Binlog 消息处理接口 | 已实现（形态不同）：并入 `BinlogToVersionConverter` |
| `processor/DefaultBinlogProcessor` | 默认实现：过滤表 → 转版本值 → 发送 | 已实现（形态不同）：同上 |
| `convert/BinlogToVersionConverter` | 把 Binlog 事件转成版本值，时钟取"库里存量时钟再把自己加一"，时间戳取 Binlog 的执行时间。转完直接交给消费者 | 已完成 |
| `convert/MySQLTypeMapper` | MySQL 类型到 Java 类型的映射 | 已实现（形态不同）：由 `convert/CourseRowMapper` 承担，只映射 `t_course` 一张表，数值解析偏宽松 |
| `listener/RocketMQBinlogListener` | canal-mq 模式专用。包装 RocketMQ 的顺序消费者，单线程消费，把 flatMessage 交给转换器。异常时挂起队列重试，坏消息跳过 | 已完成 |
| `producer/NoopVersionChangeProducer` | canal-mq 模式下业务写路径注入的空实现，发布动作什么都不做，同步改由 Binlog 链路触发 | 已完成 |
| `producer/RepairTaskProducer` | 把巡检差异发到修复队列 | 未实现 |
| `support/VersionReader` | 读取某个键的存量版本记录和时钟，给生产者拼新时钟用 | 已完成 |

### 10. hercules-ui —— 前端

Vue 3.5 + Vite 7 + TypeScript + Pinia + Vue Router + Element Plus + ECharts。宿主机构建出 `dist`，由 nginx 容器（8090）托管，`/api` 反代到网关，并且关掉了缓冲以免影响流式对话。

布局是一个壳装两端：登录后按角色进学生端或管理端，共用同一个布局组件——左边是可折叠菜单（按角色渲染不同项），上面是标题栏加用户菜单，右边是内容区。

| 端 | 左侧菜单 | 角色 |
| :--- | :--- | :--- |
| 学生端 | 课程大厅、我的选课、对话助手 | STUDENT |
| 管理端 | 治理驾驶舱、课程管理、演示工具 | ADMIN |

各页面的情况：

| 页面 | 做什么 | 要点 |
| :--- | :--- | :--- |

页面守卫：未登录跳 `/login` 并把原地址放进 `redirect` 参数；已登录但角色不在 `meta.roles` 里就跳对应端首页。前端按角色跳转只为了界面好用，权限以服务端为准。

状态管理按业务分五个 store：auth（用户名和角色）、course（列表和详情）、enrollment（选课退课与学分）、monitor（统计快照和轮询）、chat（消息流式状态机）。数据单向流动：组件只读 state，所有写操作走 action 再调 api 层。令牌不放在 store 里，在 `api/tokenBox`：accessToken 只存内存，refreshToken 存 localStorage（键 `hercules.refresh`）。

登录信息存法：accessToken 只放在内存里，不写 localStorage，减少被脚本偷走的风险；refreshToken 放 localStorage，7 天有效，服务端可以吊销。刷新页面后靠 401 自动静默刷新恢复会话，多个请求同时 401 只会触发一次刷新。

对话的前后端约定：前端 POST `/api/v1/chat`，服务端用 SSE 分片返回。`token` 事件是正文，逐片追加到最后一条回复上；`meta` 事件带候选课程和冲突信息，用来渲染卡片和按钮；流结束把整段回复存进会话历史；`error` 事件只是兜底，大模型出问题在后端就已经降级成候选列表了。前端自己写了一个 SSE 解析器，处理跨块粘包、多行 data 和 CRLF。

前端测试 17 个用例，覆盖 SSE 解析、401 单飞刷新、JWT 解码、学分合计、对话 store 重置。

## 三、模块依赖关系

按实际代码核对（2026-09-10）：

| 来源模块 | 目标模块 | 关系 | 原因 |
| :--- | :--- | :--- | :--- |
| hercules-cache | hercules-common | 编译依赖 | 实体、异常、缓存键、JSON 工具 |
| hercules-sync | hercules-common | 编译依赖 | BinlogEntry、VectorClock、CacheVersion 等模型 |
| hercules-sync | hercules-cache | 编译依赖 | 消费端要刷新缓存 |

| hercules-agent | Spring AI | 编译依赖 | 接智谱 GLM |

## 四、缓存键一览

| 键 | 存在哪 | 过期时间 | 含义 |
| :--- | :--- | :--- | :--- |
| `course:{id}` | 一级 + 二级 | 一级 60 秒 / 二级 300 秒 | 课程详情。**纳入版本链**：写数据和 Binlog 两条路都要经消费者处理（写二级、清一级、更新版本表） |
| `course:list:{page}:{size}:{keyword}` | 一级 + 二级 | 都是 10 秒 | 课程列表（关键字转小写再转义）。**不纳入版本链**，靠 10 秒的过期时间兜底 |
| `auth:refresh:{uuid}` | Redis | 7 天 | 刷新令牌白名单。用一次换一次，旧的删掉 |
| `auth:blacklist:{jti}` | Redis | 等于 accessToken 剩余有效时间 | 登出黑名单，应用层校验 |
| 回源锁 | Redis | 3 秒 | 防止缓存击穿的分布式锁，用 SET NX 加锁，用 Lua 脚本释放 |
