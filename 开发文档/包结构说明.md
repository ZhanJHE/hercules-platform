## 一、整体包结构树（目标形态：Maven 多模块）

```
hercules-platform/
├── hercules-common/               # 公共模块：工具类、常量、异常定义、向量时钟算法
├── hercules-cache/                # 缓存治理模块：多级缓存封装、Redis/Caffeine操作
├── hercules-sync/                 # 数据同步模块：Canal监听器、RocketMQ生产/消费
├── hercules-inspector/            # 巡检引擎模块：定时巡检、一致性比对、补偿SQL生成
├── hercules-agent/                # 多智能体模块：Spring AI Alibaba智能体定义与编排
├── hercules-rag/                  # RAG检索模块：向量化、Milvus操作、Graph RAG
├── hercules-gateway/              # API网关模块：路由、认证、限流
├── hercules-observability/        # 可观测性模块：OpenTelemetry配置、Metric暴露
├── hercules-admin/                # 管控台后端：运维接口、健康度计算
└── hercules-ui/                   # 前端模块：Vue3 + ECharts可视化（独立目录）
```

> MVP 阶段采用**单模块 + 分包**起步（工程 `hercules/`，包根 `com.zhanjh.hercules`），
> Sprint 2 起再按本树拆分为 Maven 多模块。映射关系见文末「四、MVP 实现映射」。

## 二、逐模块详细注释

### 1. hercules-common —— 公共基础模块

全平台的公共基座：领域模型、常量、枚举、异常与工具类。所有模块仅向下依赖本模块，不允许反向依赖。

| 类 | 详细说明 | 状态 |
| :--- | :--- | :--- |
| `model/clock/VectorClock` | 向量时钟：`(nodeId → counter)` 分量 TreeMap，提供 `increment`（本节点自增）、`merge`（逐分量取 max）、`compare`（AFTER/BEFORE/EQUAL/CONCURRENT 判定）、`isConcurrent`；写操作 `synchronized` 保护；序列化为 JSON 存入 `t_cache_version.vector_clock_json`。是 FR-HC-03 冲突消解的核心算法类。 | ✅ 实现于 `sync.clock` |
| `model/clock/VersionedValue` | 携带向量时钟的版本化值：缓存键 + 值 JSON + 产生节点 + 时间戳（LWW 裁决依据）+ 时钟；同步链路统一载荷。 | ✅ 实现于 `sync.model`（record） |
| `model/cache/CacheKey` | 缓存键构建器（前缀 + 业务 ID + 后缀），统一键命名。 | 🔄 由 `common.CacheKeys` 静态工具承担 |
| `model/sync/BinlogEntry` | Binlog 事件模型：表名、主键、变更类型、before/after 数据、时间戳、binlog 位点；Canal→MQ 链路的传输单元。 | ⏳ Sprint 2 |
| `model/sync/ChangeType` | 变更类型枚举 INSERT / UPDATE / DELETE。 | ⏳ Sprint 2 |
| `model/agent/AgentContext` | 智能体执行上下文：sessionId、traceId、userId、用户输入、对话历史与扩展元数据。 | ⏳ Sprint 5 |
| `model/agent/AgentResult` | 智能体执行结果：输出内容、状态、耗时、调试信息。 | ⏳ Sprint 5 |
| `model/enrollment/Course` | 课程实体 ↔ `t_course`（课程编码唯一，容量/已选数、上课时间与先修课 JSON 列——MVP 以 TEXT 承载）。 | ✅ 实现于 `model.Course` |

### 2. hercules-cache —— 缓存治理模块（门面模式 + 策略模式）

多级缓存统一入口：L1 Caffeine（进程内）→ L2 Redis（分布式）→ MySQL，cache-aside 读路径逐级回填；写路径配合同步链失效/刷新。

| 类 | 详细说明 | 状态 |
| :--- | :--- | :--- |
| `core/CacheManager` | 缓存门面接口：`get(key, loader)` cache-aside 读取、`put`、`invalidate`（双级失效）、`invalidateLocal`（仅 L1，演示回填用）；值统一以 JSON 字符串承载。 | ✅ 实现于 `cache.core` |
| `core/MultiLevelCacheManager` | 多级缓存实现：L1 命中→返回；L1 未命中查 L2，命中回填 L1；L2 未命中执行 loader 查 DB 并回填两级。每级路径打点命中率统计；L2 允许缺省（无 Redis 环境退化为 L1+DB）。 | ✅ 实现于 `cache.core` |
| `core/LocalCacheManager` | 本地缓存抽象接口：get/put/invalidate/estimatedSize。 | ✅ 实现于 `cache.local` |
| `core/DistributedCacheManager` | 分布式缓存抽象接口：get/put(含 TTL)/delete。 | ✅ 实现于 `cache.remote` |
| `strategy/TTLStrategy` | TTL 策略接口：按键区分详情键/列表键的本地与远端 TTL。 | ✅ 实现于 `cache.strategy` |
| `strategy/FixedTTLStrategy` | 固定 TTL 实现：列表键（前缀 `course:list:`）10s 最终一致窗口；详情键 L1 60s / L2 300s。 | ✅ 实现于 `cache.strategy` |
| `strategy/AdaptiveTTLStrategy` | 自适应 TTL：按访问频次动态调整（热点键延长、冷键缩短）。 | ⏳ 后续冲刺 |
| `strategy/EvictionStrategy` | 淘汰策略扩展点。 | ⏳（MVP 由 Caffeine 内置 W-TinyLFU 承担） |
| `stats/CacheStatsCollector` | 运行时计数器：L1/L2 命中与未命中、DB 回源、版本应用数、冲突检测数（AtomicLong）；`bindTo(MeterRegistry)` 注册为 Micrometer FunctionCounter（`hercules.cache.*` / `hercules.sync.*` 指标族）；`snapshot()` 计算总体命中率 = (L1 命中+L2 命中)/总读请求。 | ✅ 实现于 `cache.stats` |
| `stats/CacheHitRateCalculator` | 命中率计算器。 | 🔄 语义并入 `snapshot().cacheHitRate()` |
| `config/CaffeineConfig` | Caffeine 装配：expireAfterWrite 全局固定 TTL + maximumSize + recordStats。 | ✅ 并入 `CacheConfig` + `CaffeineLocalCacheManager` |
| `config/RedisConfig` | Redis 装配。 | 🔄 Boot 自动装配 `StringRedisTemplate`（Lettuce）+ `RedisDistributedCacheManager` |

### 3. hercules-sync —— 数据同步模块（观察者模式 + 策略模式）★核心

缓存一致性同步链：Binlog 事件 → 版本化消息 → 向量时钟消费者（新版本应用 / 旧版本幂等丢弃 / 并发冲突合并）→ 刷新缓存与版本表。

| 类 | 详细说明 | 状态 |
| :--- | :--- | :--- |
| `listener/BinlogEventListener` | Binlog 监听器接口：start/stop/onBinlogEvent。 | ⏳ Sprint 2 |
| `listener/CanalBinlogListener` | Canal 实现：伪装 MySQL Slave 拉取 Binlog，转换为 BinlogEntry。 | ⏳ Sprint 2 |
| `producer/VersionChangeProducer` | 版本变更生产者接口：`publish(VersionedValue)`；调用契约——业务事务内落库后调用，实现不得因传输异常中断业务事务。 | ✅ 接口实现于 `sync.producer` |
| `producer/InProcessEventBusProducer` | **MVP 传输实现**（文档树外补充）：Spring 进程内事件总线；事件由监听器在 AFTER_COMMIT 消费，保证「先提交、后同步」。 | ✅（Sprint 2 由 Canal→RocketMQ 适配器替换） |
| `listener/VersionChangeEventListener` | **MVP 事务桥**（文档树外补充）：`@TransactionalEventListener(AFTER_COMMIT, fallbackExecution=true)`——有事务则提交后消费，无事务（调试端点）立即消费；异常捕获记日志，不影响已提交业务。 | ✅ |
| `model/VersionChangeEvent` | **MVP 事件信封**（文档树外补充）：包裹 VersionedValue；Sprint 2 更换传输层后载荷结构不变。 | ✅ |
| `consumer/VersionChangeConsumer` | 版本变更消费者（含 VersionConflictResolver 语义）。决策表：比对 `t_cache_version` 存量时钟——AFTER 应用（写 L2 → 失效 L1 → upsert 版本记录）；EQUAL/BEFORE 丢弃（幂等）；CONCURRENT 字段级 LWW 合并后应用并记冲突。应用/冲突分别计数并暴露 Micrometer 指标。 | ✅ 实现于 `sync.consumer` |
| `consumer/VersionConflictResolver` | 冲突消解器。 | 🔄 语义并入 Consumer + ConflictMergeStrategy |
| `consumer/RepairTaskConsumer` | 修复任务消费者：执行巡检产生的补偿任务，更新 `t_repair_log`。 | ⏳ Sprint 4 |
| `processor/BinlogMessageProcessor` | Binlog 消息处理器接口（监听器→生产者之间的处理管道）。 | ⏳ Sprint 2 |
| `processor/DefaultBinlogProcessor` | 默认实现：过滤关注表 → 转版本化值 → 发送。 | ⏳ Sprint 2 |
| `convert/BinlogToVersionConverter` | BinlogEntry → VersionedValue 转换器（含向量时钟构建）。 | ⏳ Sprint 2 |
| `convert/MySQLTypeMapper` | MySQL 类型 → Java 类型映射（JSON 列、DATETIME(3) 等）。 | ⏳ Sprint 2 |
| `producer/RepairTaskProducer` | 修复任务生产者：巡检差异 → 修复队列。 | ⏳ Sprint 4 |
| `support/VersionReader` | **MVP 辅助**（文档树外补充）：读取缓存键的存量版本记录/向量时钟；供生产者构建 incoming 时钟（存量 ⊕ 本节点自增）与调试端点判断冲突前置。 | ✅ |

MVP 在 `hercules/src/main/java/com/zhanjh/hercules` 下按目标模块同构分包，拆分时按包平移即可：

| 目标模块 | MVP 包 | 内容 |

| hercules-common | `common` / `model` / `mapper` | R、BusinessException、JsonUtil、CacheKeys、PageResult、Course/Enrollment/CacheVersion、三个 Mapper |

| hercules-application | `HerculesApplication` | 启动类 |
| inspector / agent / rag / admin / ui | — | ⏳ 按冲刺计划实现 |
