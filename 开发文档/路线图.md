| Milvus 向量库 + Neo4j 图库 | 没用 | RAG 整体没做 |

## 八、下一步建议做的

当前首要目标：**RAG（向量增强检索，FR-MA-03 的依赖）**。按投入产出排的顺序：

1. **RAG 向量增强检索（首要目标）**。推荐方案：Redis Stack 向量检索 + 智谱 embedding-3，经 Spring AI VectorStore 抽象接入。
   - 向量库：把现有 `redis:7-alpine` 换成 redis-stack 镜像（内置 RediSearch 的 HNSW 向量索引），用 `spring-ai-starter-vector-store-redis` 接入。不新增中间件、不动其他容器；业务代码只依赖 Spring AI 的 VectorStore 抽象，将来要换 Milvus 只换实现类，业务代码零改动。
   - 向量化：智谱 embedding-3（OpenAI 兼容，走现有 GLM 接入与 API key，`/v4/embeddings`）。
   - 范围：文本切块 → 向量化 → 检索 → 命中片段拼进推荐智能体的上下文。**Neo4j 图检索不做**（当前数据量用不上，见第六节；只做向量检索）。
   - 前置条件一（数据源）：课程大纲目前只有 `syllabus_url` 占位（`/syllabus/CS101.pdf`），没有真实文本。需要先造一份 50 门课的种子大纲（每门 300~500 字，存 MySQL 或静态文件），这是 RAG 能跑起来的前提。
   - 前置条件二（embedding key）：当前 GLM API key 已销毁待重新签发，embedding 需要新 key；若新 key 一直不到位，备选本地 embedding（bge-small-zh 经 Spring AI ONNX 推理，零外部调用但引入模型文件）。
   - 备选方案：方案二 Milvus（容器栈加 etcd + minio + milvus 三个服务，贴合原计划与论文口径，但单机资源占用大，对几十门课的量级是过度设计）；方案三嵌入式向量库（LanceDB / sqlite-vec，零容器、本机直跑友好，但论文口径弱）。
2. **重新做一次压测**（必做）。现有性能数字口径已失效，论文里要用就得重测。同时建议把压测脚本的写路径改成用 `st001~st060` 这批账号（现在所有写请求都用 st001 一个账号，选课唯一键生效后会大量返回 409，而且单账号根本压不到"防超选"和"并发冲突"这两个核心机制）。
3. **补巡检引擎**（FR-HC-04/05）。`hercules-inspector` 是空模块，`t_repair_log` 建了没用，论文第 4 章把巡检引擎写在核心章节里。它同时能给上面那些已知问题兜底。
4. **补可观测性**（FR-OB-02/04）。一致性健康度评分最便宜，而且它能把缓存治理和监控两块连起来；分布式追踪要把 Zipkin 加进去。
5. **给 eBPF 一个结论**（FR-OB-01，标着 P0）。要么在 WSL2 里把 Beyla 跑起来，要么承认没做、改掉创新点摘要和需求优先级。不要留着一个标 P0 但没实现的需求。
