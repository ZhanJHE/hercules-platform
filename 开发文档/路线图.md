# 路线图

这份文件记录项目做到哪一步了：每条需求做了没有、做到什么程度、没做的差在哪。

判断依据是代码，不是设计文档。最后核对日期：2026-09-11。

相关文件：
- 开工时写的需求和设计（不再改动，作为基线）：[起步文档.md](起步文档.md)
- 每个包和类的实际情况：[包结构说明.md](包结构说明.md)
- 测试跑出来的结果：[测试报告.md](测试报告.md)
- 按时间记录的过程：[工作日志.md](工作日志.md)

状态一共三种：
- **已完成**：代码里有，并且有测试或实测数据
- **部分完成**：做了一部分，差距写在"差在哪"一列
- **未实现**：代码里没有

## 六、设计基线里定的组件，实际没用上的

| 计划用的 | 实际用的 | 原因 |
| :--- | :--- | :--- |
| Spring AI Alibaba | Spring AI 1.0.6 + 智谱 GLM | 智谱走 OpenAI 兼容协议，直接用 Spring AI 官方 starter 更简单 |
| eBPF / Grafana Beyla | Micrometer + Prometheus | 没做 |
| OpenTelemetry + Tempo | 什么都没用（只有 traceId 日志关联） | 没做 |
| Milvus 向量库 + Neo4j 图库 | 没用 | RAG 整体没做 |
| 双 Layout（学生端/管理端各一套） | 一个 AppLayout，按角色渲染菜单 | 两套布局重复代码多，合并了 |
| Vite 5 | Vite 7 | 创建工程时装的就是 7 |
| 容器内 `npm ci` 构建前端 | 宿主机先 `npm run build`，容器只放静态文件 | 受限网络下容器内装依赖超时（实测 600 秒以上） |

## 七、下一步建议做的

按投入产出排的顺序：

1. **重新做一次压测**（必做）。现有性能数字口径已失效，论文里要用就得重测。同时建议把压测脚本的写路径改成用 `st001~st060` 这批账号（现在所有写请求都用 st001 一个账号，选课唯一键生效后会大量返回 409，而且单账号根本压不到"防超选"和"并发冲突"这两个核心机制）。
2. **补巡检引擎**（FR-HC-04/05）。`hercules-inspector` 是空模块，`t_repair_log` 建了没用，论文第 4 章把巡检引擎写在核心章节里。它同时能给上面那些已知问题兜底。
3. **补可观测性**（FR-OB-02/04）。一致性健康度评分最便宜，而且它能把缓存治理和监控两块连起来；分布式追踪要把 Zipkin 加进去。
4. **给 eBPF 一个结论**（FR-OB-01，标着 P0）。要么在 WSL2 里把 Beyla 跑起来，要么承认没做、改掉创新点摘要和需求优先级。不要留着一个标 P0 但没实现的需求。
5. **RAG**（FR-MA-03 依赖它）。工作量最大。如果时间不够，只做向量检索，Neo4j 不做，并在文档里写清楚为什么。
