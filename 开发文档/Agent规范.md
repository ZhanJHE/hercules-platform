## 二、绝对不能碰的东西

### `deploy/.env` 里有一把真实密钥，而且这个文件被 git 跟踪

- 这个文件里是智谱 GLM 的 API Key。它已经进过 git 历史，且仓库是公开的。
- `.gitignore` 里写了它，但**gitignore 对已跟踪文件无效**，所以它仍然会被 `git add .` 带进去。
- **永远不要提交它。** 提交前先看 `git status`，确认输出里没有它。
- 其它凭据同理：`hercules-application/src/main/resources/application-local.yml`（本机数据库账号）和 `hercules-gateway/src/main/resources/application-local.yml`（签名密钥）也是私有文件，已 gitignore，不要提交。

### 不要改《历史基线归档.md》

它是开工时写的规划，保留原样作为对照。它已经过时，不要按它做事，也不要"顺手修正"它。

### 不要重写《工作日志.md》里过去的条目

那是过程记录，改了就丢历史。新增条目写在该文件末尾，用第二节的文风规则。

## 三、怎么跑测试

### 后端

```powershell
# 正常环境
cd hercules-platform
.\mvnw.cmd test          # 108 个用例

# mvnw.cmd 报 'powershell' 不是内部或外部命令 时（PATH 里没有 Windows PowerShell）
mvn -f pom.xml test
```

**在受限沙箱（禁止子进程管道）里**，surefire 分叉 JVM 会失败，报 `CreatePipe error=5`，Mockito 也会因为无法自附加而失败。用这个组合可以在单个 JVM 里跑通全量：

```powershell
$env:MAVEN_OPTS="-Djdk.attach.allowAttachSelf=true"
mvn -B -f pom.xml test -DforkCount=0
```

### 前端

```powershell
cd hercules-platform/hercules-ui
npm test          # Vitest，17 个用例
npx vue-tsc -b    # 类型检查，必须零错误
```

前端测试需要 esbuild 起子进程，受限沙箱下会报 `spawn EPERM`，放宽进程权限后才能跑。

### 测试纪律

- **不依赖外部中间件**：用 H2 内存库加内存桩，不能要求本机有 MySQL 或 Redis。
- **不依赖网络**：调大模型的地方一律注入 `StubLlmPort`，真实 GLM 只在容器端到端验证时用。
- 新增用例要同步更新[测试报告-2026-09-11.md](测试报告-2026-09-11.md)里的数量。

## 四、写代码的规则

### 依赖方向不可反向

```
common ← cache ← sync ← agent ← application
```

- `hercules-agent` **不能**依赖 `hercules-application`。它需要什么业务能力，就在 `port/` 下声明接口（现在有 `CourseQueryPort`、`EnrollmentPort`），由 application 侧的 `AgentPortAdapter` 实现。
- `hercules-gateway` 和 `hercules-ui` 是独立进程/工程，不参与 Maven 依赖。

### 缓存键不要手拼字符串

统一走 `common.CacheKeys`。键的格式、TTL 和语义写在[包结构说明.md](包结构说明.md)第四节。

### 新增配置项要三处齐

1. 属性类里加字段和 getter/setter，**setter 里做校验**（非法值直接抛异常拒绝启动，跟现有风格一致）；
2. `hercules-application/src/main/resources/application.yml` 里加默认值并写中文注释；
3. 如果影响使用方式，更新[环境配置与部署.md](环境配置与部署.md)。

### 注释用中文，跟现有风格

类头 Javadoc 写清楚：这个类是干什么的、线程安全性、已知边界。字段和方法用一句话说明。带 `@author` / `@since`。不要写"本模块是系统核心"这类没有信息量的话。

### 数据库表结构改动要写升级步骤

`schema.sql` 用的是 `CREATE TABLE IF NOT EXISTS`，**对已有的库不生效**。加了唯一键或列之后，要在[环境配置与部署.md](环境配置与部署.md)第一节的"存量库升级"里补上可直接执行的 SQL。

## 五、写文档的规则

这是这个项目最容易出问题的地方：文档写了但和代码不一致，比没有文档更糟。

### 铁律：改功能必须在同一个提交里更新《路线图》

改了什么需求的状态（做完了 / 还是没做），就在[路线图.md](路线图.md)里改掉。否则路线图会变成第二份说谎的文档。

### 文风

- 用中文。句子短，一句话说一件事。
- **不用 emoji**，不用装饰性加粗，不用"闭环""赋能""抓手"这类堆砌的词。
- 不在文档里承诺没做的事。**没做的要明确写"未实现"**，并说清楚差在哪。
- 类名、方法名、表名、字段名、配置键、接口路径**照抄代码**，不要翻译、不要美化。

### 文件名与链接

- 文件名用中文。`README.md` 是例外——仓库首页只认这个名字。
- 文件名带日期的文档（如测试报告），日期是最后更新日期。改了要同步所有指向它的链接。

### 图

- 架构图和流程图用 **HTML** 维护（就是[项目讲解.html](项目讲解.html)），不再用脚本生成 PNG，也不要引入需要联网才能显示的库——这个文件要能离线打开。
- 改架构或改请求流程时同步更新这份 HTML，别只改代码。

### 文档分工（别在一份里塞两件事）

| 文件 | 只管 |
| :--- | :--- |
| `README.md` | 是什么、怎么跑、现在做到哪、文档索引 |
| `项目讲解.html` | 分层结构、模块划分、四类请求的调用流程 |
| `路线图.md` | 需求状态、风险兑现情况、下一步 |
| `包结构说明.md` | 代码结构：包、类、缓存键、接口、页面路由 |
| `设计说明.md` | 认证/日志/前端的设计取舍与偏差 |
| `环境配置与部署.md` | 安装、启动、排错、存量库升级 |
| `测试报告-<日期>.md` | 测试与压测的实测数据 |
| `工作日志.md` | 按时间的过程记录与踩坑 |
| `历史基线归档.md` | 开工时的规划（只读） |

## 六、提交规则

提交信息用中文，格式是 `类型: 主题——要点`，类型沿用现有习惯：

- `feat:` 新功能（如 `feat: 阶段 D——多智能体对话入口...`）
- `fix:` 修缺陷（如 `fix: 安全与缺陷修复轮——...`）
- `docs:` 只改文档
- `chore:` 清理、配置、杂项
- `refactor:` 重构，行为不变

其它要求：

- 提交前跑全量测试（后端加前端）。
- 不要提交 `target/`、`node_modules/`、`dist/`、`loadtest` 的运行时和报告产物，以及 `logs/`。这些已在 `.gitignore` 里。
- 工作区要干净，不要留调试用的临时文件。

## 七、回答项目所有者时的规则

- 说结果，不要罗列过程。做了就说做了，没做就说没做，**不要用"基本完成"掩盖缺口**。
- 数字要给出来源（哪个文件、哪一节），不要凭印象说。
- 发现文档和代码不一致，直接指出来，并说明以代码为准。
- 沙箱或环境导致的失败，要说明是**环境限制**还是**代码问题**，不要混在一起说。
