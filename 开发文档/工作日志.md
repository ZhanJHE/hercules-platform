### 已知事项与后续待办（注释工程发现汇总，答辩备查）

> 来源：五路注释任务的「只报告不修改」清单，按主题归并。

#### API/校验类

1. `@NotNull` 校验实际不生效：控制器参数未加 `@Valid`，缺 courseId 表现为 404「课程不存在： null」而非 400；缺 studentId 会落库 null（Sprint 2 收紧）→ 当日已修复（见补记）。
2. 无重复选课约束：应用层不查已有 status=1 记录，`t_enrollment` 亦无唯一约束，可重复选课致 enrolled 与记录数失衡。
3. 列表缓存键未转义：keyword 含 `:` 时键段可能碰撞；"Java"/"java" 键分裂；page/size 无边界校验（size 大值可单页拉全表）→ 键碰撞当日已修复（百分号转义）；大小写分裂与分页边界保留（不影响正确性）。
4. 500 响应携带原始异常消息，可能泄漏内部细节，上线前收紧。

#### 演示注意类

5. 连续两次 `simulate-conflict`：第二次 `{node-sim:1}` 相对存量时钟为 BEFORE 被幂等丢弃。答辩演示前需先在 node-1 发生一次选课/退课。
6. `simulate-conflict` 不写 `t_course`，TTL 过期回源后课程名还原（演示窗口期注意）。

#### 并发/一致性类

7. `CacheVersion` upsert 为 select-then-write 无锁：单实例（进程内总线串行驱动）安全；多实例需乐观锁或 `cache_key` 唯一键冲突重试。
8. `FieldLwwMergeStrategy` 为「字段并集 + LWW」叠加语义：新值时间戳更旧时，仅新值存在的字段仍会并入（严格 LWW 应整体保留旧值）。答辩追问时需备好说辞。
9. 冲突合并的旧值取自 L2：L2 被逐出时退化为整体采用新值，仅存于旧值的字段丢失（冲突路径已知盲区）。

#### 数据库类

10. `enrolled`/`capacity` 仅靠条件 UPDATE + 应用层校验，无 DB CHECK 兜底。
11. JSON 列以 TEXT 承载（与起步文档 JSON 类型有偏差，Sprint 2 如需 JSON 函数再切换）。

#### 代码卫生类

12. `VectorClock.fromJson` 的 merge 函数为防御性死代码（Jackson 解析阶段重复 key 已被后者覆盖）。
13. `STATUS_PRESELECT` 为无写路径的预留常量；`withdraw` 的 409 分支正常数据不可达（防御代码）。
14. `HerculesSyncProperties.maxNodes` 无下限校验；事件监听器对 null 载荷兜底不闭合。
15. L1 列表键短 TTL 不生效（cache 注释任务发现）：Caffeine 原实现忽略逐键 TTL 参数，列表键在 L1 按全局 60s 过期，「10s 最终一致窗口」仅 L2 生效 → 当日已修复（自定义 Expiry，见补记）。
16. 测试健壮性备注：`concurrentVersionIsMergedWithLww` 的 LWW 胜负依赖系统时钟不回拨（正常恒成立）；`readLong` 的 JSON Pointer 转换（`"$.x"`→`"/x"`）经实测行为正确。

## 2026-09-05（周四）· 阶段 A+：高可用与容错加固

### 背景

评审发现四个风险点（全部属实）：① Lettuce 未配超时（默认命令超时 60s，Redis 挂起会拖垮 Tomcat 线程池）；② Redis 路径无熔断降级；③ `get(key, loader)` 无击穿防护（热点键过期瞬间并发全量回源）；④ Hikari/MyBatis/事务均无超时传递。

### 完成事项（四道防线）

1. 超时传递（application.yml）：`spring.data.redis.timeout=200ms`、`connect-timeout=500ms`；HikariCP `maximum-pool-size=20`、`connection-timeout=3000`；MyBatis `default-statement-timeout=3`（秒）；`EnrollmentService` 两事务方法 `@Transactional(timeout = 5)`。
2. Redis 熔断降级：新增 `ResilientDistributedCacheManager` 装饰器（Resilience4j 2.4.0，程序化包装）。参数：计数窗口 50、最少 10 次判定、失败率 50%、慢调用阈值 300ms / 占比 80%、OPEN 10s 自动转半开、半开放行 2 次探测。降级语义：get→null（读路径落 DB）、put→跳过、delete→重试 1 次后跳过（残留旧值上界=剩余 TTL，已知取舍）。新增 `isAvailable()` 接口方法供读路径跳过 L2。
3. 击穿防护（两级）：新增 `SingleFlight`（进程内单飞：ConcurrentHashMap+Future，同键仅一个队长回源，等待者 6s 预算，失败不缓存）+ `CacheLoadLock` 抽象（`RedisCacheLoadLock`：SET NX PX + Lua 比对令牌释放，异常一律按未抢到处理；`NoopCacheLoadLock`：开关关闭/无 Redis 时恒抢到）。`MultiLevelCacheManager` 读路径重构为「L1 → L2 探测（isAvailable 门控）→ 单飞{ 双检 → 分布式锁/轮询 → 安全阀 }」。
4. 可观测：`CacheStatsCollector` 新增 `redisDegraded` 计数与 `redisCircuitState` 状态（装饰器每次操作后采样）；stats 端点与 Prometheus（`hercules.cache.redis.degraded`、`hercules_cache_redis_circuit_state` gauge）双出口暴露。

### 踩坑记录

- Resilience4j 2.4.0 API 变更：`TaggedCircuitBreakerMeterBinder` 已被 `TaggedCircuitBreakerMetricsPublisher` 取代、`CircuitBreaker.getEventConsumer()` 已不在接口上 → 放弃官方 binder，改为「状态 gauge 直绑 getState() + protect() 调用后采样同步」，零 API 风险；
- 构造器内 `this(...)` 委托参数不能调用实例方法 → `defaultConfig()` 改 static；
- 测试 bug 两处：桩失败次数预留过多导致半开探测仍失败（应为恰好耗尽）；测试 loader 是 Supplier 不能抛 InterruptedException（sleep 需自捕获）。

### 验证

- 单测 46/46 全绿（cache 21 + sync 19 + application 6；新增熔断状态迁移/慢调用熔断/删除重试/单飞合并/单飞失败重试/锁互斥与容错等 11 个用例）；
- 真机故障演练（黑洞监听器 6390 模拟 Redis 挂起，应用指向黑洞；不触碰真实 Redis 6379）：
  - 故障期：miss 路径首次 3.4s（建连+命令超时的有界代价）→ 熔断 OPEN 后 7-8ms（原方案会是 60s×N 拖垮线程池）；15 同键请求 dbLoad=1（单飞生效）；故障期间选课照常成功（256ms，DB 事实源 + 同步链 put 降级跳过）；
  - 恢复期：黑洞换为 6390→6379 TCP 转发器 → 10s 后半开探测成功 → 两次探测后 CLOSED；L2 经真实 Redis 回填（l2Hit=1，8ms 命中），降级计数不再增长。

### 结论

四个风险点全部处理完毕：最坏路径延迟有界（L1 µs / L2 200ms / DB 3s / 事务 5s），Redis 故障期间系统照常服务（读直连 DB、写不受影响），恢复后自动回切。提交并同步 GitHub。

## 2026-09-07（周一）· 阶段 H-4 压测：JMeter 调试修复 + 500 并发阶梯压测

### 背景

压测脚本连番受阻：setup 登录 200 但所有压测请求 401；部分线程 StackOverflowError 死亡；线程组 0 线程或线程一轮即停。用户要求"出现问题停下汇报"，逐层定位后按"无聊计划"原则重构。

### 排查与根因（按时间线）

1. `jmeter:run` 目标不存在 → 插件 3.8.0 实为 `jmeter:jmeter`，且需先 `jmeter:configure`；
2. JMX ClassCastException（RegexExtractor 后缺 `<hashTree/>`）→ JMX 规范：每个元素后必须跟（可为空的）hashTree；
3. setup 登录 415→500 → setup 采样器缺 Content-Type 头（JMX 补齐 + 后端补 415 处理器）；
4. 读日志管道 bug 误导两轮排查：字符串数组取 `$_.Line` 输出恒空 → 改用 `Select-String`/`$_` 直读后立即抓到真凶；
5. StackOverflowError 根因：Once Only Controller + 配置元素组合，每次迭代开始 `recoverRunningVersion` → `hashCode` 无限递归（调用栈实证 `TestElementProperty.hashCode` 循环），线程死亡、采样停止；
6. 401 根因：Header Manager 的线程变量 `${token}` 求值时机不稳——setup 已提取合法 JWT（len=304，日志实证）但主线程请求头仍为空，网关验签失败；
7. `-J` 传参字面量：`-Jthreads=$Threads` 直达 JMeter 未展开（jmeter.log 实证）→ 0 线程；改为参数数组回显 + 全参数走 `-q` 属性文件；
8. 线程一轮即停：每线程恰 3 采样（1 读迭代 + 1 写迭代）后退出、测试在 rampup 结束时提前收尾——嫌疑锁定 ThroughputController perThread 语义（翻转 continue_forever 无效）。

### 方案重构（"无聊计划"原则，见测试报告 §6.4）

- 删除：setup 线程组、Once Only、BeanShell、ThroughputController——全部冷门组合清除；
- JMX 仅剩：双线程组（读 70% / 写 30%，用线程组规模建模流量比例）+ TestPlan 级 HeaderManager + 3 个 HTTP 采样器，计划内零脚本；
- token：登录移交 `run-loadtest.ps1`（Invoke-RestMethod，每级重新登录规避 30min 过期），写属性文件，Header 读 `Bearer ${__P(token)}`；
- 看门狗：`Start-Process -PassThru` + `WaitForExit(rampup+duration+180s)` 超时强杀，JTL 已落盘可 `-g` 重生成报告。

### 结果（分端点明细见测试报告 §六）

1. 冒烟：5 线程 728/s、20 线程 3,470/s，均 0 错误——重构后一次通过，此前全部卡点消失；
2. 阶梯：100 并发 4,051/s（0 错）→ 300 并发 4,630/s（0 错）→ 500 并发 5,027/s（3,018,549 请求，20 错 = 0.0007%）；

### 结论

## 2026-09-07（周一）· JVM 参数调研与单机共置口径分析（A/B 复跑）

### 背景

压测完成后三问：JVM 参数有无提升空间？JMeter 与被测同机共置是否合理？CPU 抢占是否使结果失去参考性？

### 现状盘点（docker exec PrintFlagsFinal 实证）

1. app/gateway 容器 JVM 全默认（`ENTRYPOINT java -jar` 零参数、容器无内存限制）→ JVM 自适应 Xms250M / Xmx4G（16GB VM 的 25%）——起步过小、上限过大；gateway 轻量服务也自适配 4G 上限；
2. 宿主 i5-12400F 仅 6 物理核/12 逻辑核；WSL2 默认占满 12 逻辑核 + 16GB；JMeter（同宿主）与 VM 共争物理核——CPU 抢占客观存在。

### 参数落地（compose + 压测脚本）

- app：`mem_limit 3g` + `JAVA_TOOL_OPTIONS="-Xms1g -Xmx2g -XX:+AlwaysPreTouch -XX:MaxGCPauseMillis=50 -Xlog:gc*:…"`（G1 保留：6 核上 ZGC 得不偿失；PreTouch 消除扩堆抖动；GC 日志供论文取证）；
- gateway：`mem_limit 1g` + Xms256m/Xmx512m；app 加 `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=40`（对症 Hikari 饱和）；MySQL/Redis 暂不加限额避免引入新变量；
- JMeter 客户端：`-Xms1g -Xmx4g -XX:+UseParallelGC`（客户端重吞吐）；
- 容器内 PrintFlagsFinal 验证全部生效（Xmx 2G/512M、AlwaysPreTouch=true、G1PauseTarget=50ms）。

### A/B 对比（L3 同参数 500 并发/10min 复跑）

| 指标 | 基线（默认 JVM + Hikari20 + 客户端 G1） | 调优后 | 变化 |
| --- | ---: | ---: | :--- |
| 总吞吐 | 5,027/s | 4,317/s | -14% |
| 错误 | 20 | 0 | Hikari 扩容根治 |
| 写吞吐 / 写 P95 | 228/s / 1651ms | 424/s / 513ms | +86% / -69% |
| 读吞吐（合计） | 4,802/s | 3,894/s | -19% |
| app GC | 无日志 | 695 Young / 0 Full / avg 6.5ms / 总耗时 0.76% | 排除 app GC |

解读：写路径收益明确（Hikari 直接受益）；读路径回退无法归因于 app GC——嫌疑为 JMeter ParallelGC 客户端 STW 与 gateway 512m 堆 GC 频率（多变量同时变更的方法局限，如实记录，列为单变量后续实验）。

### 共置口径结论（量化）

容器 CPU 采样（30s 粒度）：app 稳态 ~4.3/12 核（36%）、gateway ~2.3、mysql ~1.3——服务端合计 ~8 核，非 CPU 饱和 → 基线 5027/s 的封顶方不在 app CPU。共置压测的相对比较有效（阶梯/调优 A/B/瓶颈定位），绝对吞吐是上界口径（含客户端与宿主封顶）；CPU 抢占不毁掉参考性，但结论须分两类：机制性/相对性（有效）与绝对容量（需标注）。可选进阶：`.wslconfig` 限核 + JMeter 绑核（需 WSL 重启）；展望第二台压测机。

### 结论

JVM 有调优空间但非免费午餐：可靠性收益（错误清零）与写路径收益明确，吞吐回退待单变量归因；参数已固化 compose/脚本，GC 日志持续落盘；共置口径与证据写入测试报告 §6.5/§6.6。

## 2026-09-10（周四）· 阶段 B：真实 Binlog 同步链（Canal 1.1.7 + RocketMQ 4.9.4）

### 目标与结构

把缓存刷新的触发源从进程内事件总线替换为 MySQL Binlog → canal-server（MQ 模式）→ RocketMQ → 应用消费者：业务事务只落库（事务内的课程重读与存量时钟加载一并省去，写路径削峰），缓存刷新完全异步。`hercules.sync.transport` 一处开关：`in-process`（默认，单机/测试形态不变）/ `canal-mq`（容器栈形态）。

关键设计：①应用只依赖 `rocketmq-client 4.9.4`（不用 spring-boot-starter，规避 Boot 3 兼容问题），canal server 直接投递 flatMessage；②向量时钟在消费侧构建（VersionReader 存量 ⊕ node-id 自增，时间戳取 binlog es），语义与进程内发布一致，消费端判定/合并/落版本表代码零改动；③只订阅 `hercules.t_course`（版本链仅详情键）；④行 → Course 映射保证值 JSON 字段结构与进程内形态一致（LWW 逐字段合并前提）。

#### P0 安全

1. 对话会话越权（真实漏洞）：`/api/v1/chat` 与 `/api/v1/chat/history/{sessionId}` 原以客户端传入的 sessionId 为唯一键且不校验归属——猜到 sessionId 即可读他人对话记录，并可劫持同一 sessionId 下已登记的待确认选课。修复：`ConversationHistory` 增会话归属表（sessionId 首次使用时绑定 userId），POST 走 `claim`（首次登记 / 已登记校验），GET 走 `isOwnedBy`（只读判定，不登记新会话，避免随机 sessionId 探测撑大内存）；不匹配统一抛 `BusinessException(403)`，复用既有全局异常处理器与响应体约定。前端配套三处：登出 `clearLocal()` 一并重置聊天 store（否则同标签页换账号会沿用旧 sessionId 直接 403）、`api/chat.ts` 单独处理 403 并回调 `onSessionInvalid`、store 收到后重建会话并提示重发；同时修正 `reset()` 未复位 `sending/controller` 的隐患（否则会永久停在「发送中」）。

### 启动过程中踩的坑

netsh int ipv4 set dynamicport tcp start=49152 num=16384

## 2026-09-11（周五）· 修复 simulate-conflict 重复调用静默失效

### 问题

上一条的试运行记录了这个问题：`POST /api/v1/debug/simulate-conflict` 发出的向量时钟固定是 `{"node-sim":1}`。第一次调用能正常触发并发合并，但合并之后版本表里就存下了 node-sim 分量，再对同一个键调用时新时钟被存量时钟支配、被消费端判为过期消息丢弃，**而接口仍然返回 `published:true` 和"消费端已同步应用"**——现场连点两次，第二次没有任何反应也看不出原因。

### 改法

1. **模拟时钟的 node-sim 分量改成「存量时钟里 node-sim 的值 + 1」**，不再固定写 1。这样每次调用都严格大于上一次，一定不会被存量支配。仍然只携带 node-sim 一个分量、不带真实节点的分量，所以与本地已提交的改动互不支配，CONCURRENT 的性质保持不变。
2. **响应不再用固定文案谎报结果**。新增两个字段：
   - `relation`：本次的支配关系判定（CONCURRENT / AFTER / EQUAL / BEFORE）；
   - `effect`：对应的一句话说明，例如「并发冲突：走字段级合并，课程名取模拟值，其它字段保留原值」；
   - 另外返回 `storedClock`，方便对照。
   这样即使某次确实没触发合并（例如该课程从未被真实写过，没有可冲突的对象，会判 AFTER），调用方也能一眼看出来，而不是被"已同步应用"糊弄过去。
3. `storedVersionBefore` 的文案从"（无存量版本，本次按新版本应用，未触发冲突）"简化为"（无存量版本）"——是否触发冲突交给 `relation`/`effect` 表达，避免两处说法不一致。

方法注释同步改写：原来写的是"必走 CONCURRENT 分支"，这个前提只在"该键此前有过真实写入"时成立，原文表述过强。

### 回归测试

新增 `DebugControllerTest`（Mockito，5 例）：

| 用例 | 断言 |
| :--- | :--- |
| 首次调用 | 存量 `{node-1:1}` → 判 CONCURRENT；时钟只含 node-sim 一个分量 |
| 上次合并后再调用（缺陷回归） | 存量 `{node-1:1,node-sim:1}` → 仍判 CONCURRENT，且 node-sim=2 |
| 连续两次调用（缺陷回归） | 按消费端行为推进存量时钟，两次都必须判 CONCURRENT |
| 无存量版本 | 判 AFTER，`effect` 明确写"不是并发"，不谎报已合并 |
| 并发场景的响应 | `relation=CONCURRENT`、`effect` 含"字段级合并"、`storedClock` 正确 |

### 验证

- 后端全量 **113/113 通过**（新增 5 例），`BUILD SUCCESS`；
- 重新打包并重启应用后现场实测：对同一门课**连打三次** simulate-conflict，三次都判 CONCURRENT，
  `conflictDetected` 依次 0→1→2→3，课程名每次都取模拟值，学分和教师字段始终保留（字段级合并生效）：

### 另外记录一个测试写法上的坑

顺序调用两次的那个用例一开始红了：辅助方法里用 `verify(producer)`（要求恰好一次），而 Mockito 会记录该 mock 的全部调用，两次调用就报 `TooManyActualInvocations`。改用 `verify(producer, atLeastOnce())` 并取最近一次捕获的值即可——是测试写法问题，不是实现问题。
