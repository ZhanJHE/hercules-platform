### 6.3 瓶颈定位与分析

1. **吞吐平台化于 ~5,000 req/s**：并发 100→300→500，吞吐 4,051→4,630→5,027 增益递减，均值延迟 23→62→97ms 近线性抬升——系统进入饱和区；
2. **写路径瓶颈：Hikari 连接池饱和**。L3 期间应用日志实证：`HikariPool-1 - Connection is not available, request timed out after 3000ms (total=20, active=20, idle=0, waiting=116)`——150 写并发下 20 连接耗尽，排队超 3s 的请求按阶段 A+ 全链路超时设计**快速失败**（500），而非无限堆积拖垮 Tomcat 线程池（20 次失败全部为此因，无超时挂起、无错误扩散）；
3. **读路径稳如磐石**：多级缓存扛住约 4,800 读/s（两读端点合计），0 错误、P99 ≤300ms——L1/L2 命中路径在满压下未回源劣化，缓存设计目标达成；
4. **口径声明**：压测机与被测栈同宿主（Windows + WSL2 VM），~5,000 req/s 处 JMeter 客户端与宿主资源都可能参与封顶；本数据用于阶梯对比与瓶颈定位，非集群化绝对容量上限；
5. **改进方向**（衔接路线图）：写路径削峰治本是**阶段 B 的 RocketMQ 异步化**（选课事务只落 DB，版本事件异步分发，削平同步链瞬时压力）；工程优化项含 Hikari 池参数调优、JDBC `rewriteBatchedStatements`。

### 6.4 压测工具踩坑记录（过程详见《工作日志》2026-09-07）

### 6.5 单机共置口径与 CPU 抢占分析（JMeter 与被测同宿主）

**结论：共置做法合理，但必须区分两类结论的有效性。**

1. **仍然有效**的结论：阶梯趋势与相对比较（同环境下 A/B 对比双方承受同样抢占）；瓶颈定位（Hikari 饱和是服务端日志证据，与抢占无关）；错误率行为验证（3s 快速失败设计）；缓存/超时等机制性验证；
2. **需标注口径**的结论：绝对吞吐（5,027/s）是"这台机器共置形态"的数字，含 JMeter 客户端与宿主调度封顶，不能外推为服务端集群容量；
3. **量化证据**（调优后 L3 期间容器 CPU 采样，30s 粒度）：app 稳态 **~4.3/12 逻辑核（36%）**、gateway ~2.3 核、mysql ~1.3 核——**容器合计 ~8 核，VM 尚有余量，服务端并非 CPU 饱和**；基线 5,027/s 平台化的封顶方不在 app CPU（嫌疑为 JMeter 客户端 GC/调度与网关侧）；
4. **宿主事实**：i5-12400F 仅 6 物理核/12 逻辑核，WSL2 默认占满 12 逻辑核 + 16GB，JMeter 与 VM 共争物理核——抢占客观存在，但"占满逻辑核"≠"服务端 CPU 瓶颈"，以容器侧实测为准；
5. **改进选项**：本期已做（JMeter 加堆 + ParallelGC 降客户端 GC 频率；容器显式 mem_limit 隔离邻居效应）；可选进阶：`.wslconfig` 限制 WSL2 核数 + JMeter `Start-Process -ProcessorAffinity` 绑定其余核（需 WSL 重启）；展望：第二台压测机/云主机分离流量发生器。

### 6.6 JVM 参数与连接池调优 A/B 对比（L3 同参数复跑）

**变更清单**（多变量同时变更，解读时注意）：

| 对象 | 基线 | 调优后 |
| :--- | :--- | :--- |
| app JVM | 全默认（自适应 Xms250M/**Xmx4G**） | Xms1g/Xmx2g + AlwaysPreTouch + G1 MaxGCPauseMillis=50 + GC 日志 |
| gateway JVM | 全默认（自适应 Xmx4G） | Xms256m/Xmx512m + AlwaysPreTouch |
| 容器限额 | 无（cgroup=max） | app 3g / gateway 1g |
| Hikari 池 | 20（L3 实证饱和 waiting=116） | **40** |
| JMeter 客户端 | Xms1g/Xmx2g + G1 | Xms1g/Xmx4g + ParallelGC |

**结果对比**（500 并发/10min 同参数）：

| 指标 | 基线 | 调优后 | 变化 |
| :--- | ---: | ---: | :--- |
| 总吞吐 | 5,027/s | 4,317/s | -14% |
| 错误 | 20（Hikari 超时） | **0** | ✓ 写路径可靠性根治 |
| 写吞吐 | 228/s | **424/s** | **+86%** |
| 写均值 / P95 / P99 | 641 / 1651 / 2239ms | **345 / 513 / 636ms** | **-46% / -69% / -72%** |
| 读吞吐（两端点合计） | 4,802/s | 3,894/s | -19% |
| 读均值 / P95 | ~70 / ~120ms | ~88 / ~145ms | 回退 |
| app GC | 未记录 | 695 次 Young / **0 Full** / avg 6.5ms / P95 12.8ms / 总耗时 **0.76%** | app GC 非瓶颈 |

**解读**：

1. **Hikari 20→40 是明确收益**：写吞吐 +86%、写延迟近乎减半、20 个连接超时错误清零——直接对症 §6.3 定位的瓶颈；
2. **读路径回退 -19% 无法归因于 app GC**（实测仅占 0.76% 时间、0 Full GC）；嫌疑集中于 JMeter 客户端（ParallelGC 4g 堆在共享 6 物理核上的 STW 行为）与 gateway 512m 堆的 GC 频率——**列为后续单变量实验**（逐项回退对比），本报告如实记录多变量方法局限；
3. 总吞吐 -14% 主要由读路径回退贡献；写路径的确定性收益独立成立；
4. **结论**：JVM 层确有调优空间但非免费午餐——可靠性收益明确（错误清零）、写路径收益明确、吞吐回退待单变量归因；参数已固化进 compose 与压测脚本，GC 日志持续落盘供论文取证。
